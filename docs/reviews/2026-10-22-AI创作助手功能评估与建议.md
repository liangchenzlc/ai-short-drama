# AI 创作助手功能评估与建议

评估日期：2026-10-22。范围：`backend/src/short_drama/agent`、`backend/src/short_drama/service/assistant_*`、`frontend/src/features/ai-assistant`、`frontend/src/features/agents`。依据为源码直读与本地实测，未调用任何真实模型或媒体供应商。本文只做评估，未修改业务代码。

## 1. 结论摘要

功能面已相当完整：从会话、上下文快照、五层记忆、结构写入、媒体生成到批次撤销都有实现与测试。主要问题不在"缺功能"，而在三处：

1. **真机验收被一个测试参数错误卡住**，整系统最大的未知（真实模型能否驱动这套工具）至今零证据。已定位并实测复现，修一个字符串即可重跑。
2. **写入授权用正则匹配固定句式**，用户换个说法就静默降级为纯聊天。这是当前最影响体感的设计选择，且随功能增多线性恶化。
3. **约束性代码与文档的增长快于产品验证**，护栏描述已淹没契约本身，后续接手成本偏高。

## 3. 关键发现

### 3.1 P0：真机验收零通过，根因是测试参数写错（已实测）

实施记录把 Agnes 七项失败登记为"配置、夹具或兼容性检查的具体原因尚未调查"。实际原因很明确：

`agent/model_gateway.py:74-77` 的映射表只认两个值：

```python
protocol = {
    "chat-completion": "openai_chat.v1",
    "openai-response": "openai_responses.v1",
}.get(profile.protocol)
```

而 `tests/integration/standard/assistant/test_global_assistant_agnes_live.py:40` 用的是 `getattr(request, "param", "chat")`，parametrize 传的也是 `"chat"` / `"responses"`。同目录其他 broker live 测试文件用的是正确值 `"chat-completion"` / `"openai-response"`。

本地实测（`backend/.venv`，未联网）：

```text
chat             -> REJECT unsupported_agent_protocol
responses        -> REJECT unsupported_agent_protocol
chat-completion  -> openai_chat.v1
openai-response  -> openai_responses.v1
```

即七项失败发生在 `assistant_task_service.py:572` 的 `select_agent_protocol()` 准入处，根本原因是夹具传了非法枚举值，与供应商能力、助手准入逻辑均无关。

**顺带暴露的产品问题**：`ModelRuntimeProfile.protocol` 是 `str(min_length=1)` 的自由字符串（`schemas/model_runtime_profile.py:16`），而实际只有四个值可用、其中两个支持助手。合法值域既无枚举约束也无前端下拉，配置错误只能等到运行时 422。

### 3.2 P0：写入授权依赖正则匹配固定句式

`agent/standard_tools.py:75` 起、`canvas_tools.py:55` 起、`media_tools.py:71` 起、`memory_tools.py:38` 起都用 `re.fullmatch` 解析用户原文来判定授权范围。10 个真实语气样本的实测结果：

| 输入 | 结果 |
| --- | --- |
| 创建两个分镜 | OK |
| 创建一个角色和两个分镜并关联：雨夜追凶 | OK |
| 帮我创建两个分镜 | OK |
| 删除分镜 ID 123 | OK |
| 加两个镜头，一个雨夜，一个清晨 | MISS |
| 再增加三个分镜 | MISS |
| 给林晚加一场哭戏 | MISS |
| 把刚才那个分镜删了 | MISS |
| 需要两个分镜 | MISS |
| 先把角色改成更冷一点 | MISS |

命中的四条都是照抄文档句式；口语化一遍即失效。失效后的表现是"降级为纯讨论"，模型无法解释为什么没执行，用户也拿不到可操作提示。而前端首屏引导（`AssistantConversationBody.tsx:311`）只有三条纯讨论提示（"帮我梳理故事的节奏与冲突"等），完全没有传达"执行需要特定说法"。

这个设计的初衷是安全（不让模型自我授权），但把意图识别压进了正则，代价是：
- 表达自由度与功能数量成反比；
- 每加一个动作就要加一条正则分支，测试随之膨胀；
- 文档里"当前支持有界直接表达"这类免责句已经出现十余次，说明设计者自己也清楚边界不可控。

### 3.3 P1：上下文预算硬编码，与模型窗口脱节

`agent/context_budget.py:8-11`：

```python
CONTEXT_TOKENS = 65536
TOOL_RESULT_TOKENS = 4096
SAFETY_TOKENS = 2048
MEDIA_TOKENS = {"image": 2048, "video": 8192, "audio": 16000}
```

常量写死、不可配置，且按 UTF-8 字节数／3 估算而非真实 tokenizer。主流文本模型当前窗口普遍 128K 以上，65,536 会在长任务里提前触发 `paused_budget`；反过来对真正的小窗口模型又不够保守。凭证的模型配置里已有 `runtime_profile`，加一个窗口字段即可按模型区分。

### 3.4 P1：前端核心组件过载

`AssistantConversationBody.tsx` 373 行内含 26 个 `useState`、7 个 `useEffect`、19 行超过 300 字符（最长 678 字符，出现在第 317 行的 Bubble.List 内联渲染）。`CreativeAssistantPanel.tsx` 的 JSX 几乎整段压缩在单行。功能正确，但改动风险与 review 成本偏高：任何一个状态联动都需要把整段超长表达式读完。

### 3.5 P2：四代协议与文档体量

- V0/V1/V2/V3 四代协议共存，服务端旧写入口仍在（`docs/api/assistant.md` 明确"不能声称这些服务端写入口已全部退役"）。历史只读是产品要求，但代码分支与文档都要双份维护。
- `docs/api/assistant.md` 352 行，七份专题加实施记录 431 行。大量篇幅在描述护栏（"不能声称""不得当成""保守拒绝"），接口契约本身被稀释。这既是设计严谨的体现，也说明约束已多到需要专门文献承载。
- `reconciling`（供应商受理不明）状态至今没有通用人工核实接口，任务可能长期占用预占额度。这是登记在案的第 3 项未完成工作，属于真正的功能缺口，不是文档问题。

## 4. 建议

### P0-1 解锁真机验收（预计半天，收益最大）

1. 把 `test_global_assistant_agnes_live.py:40` 的默认值与 parametrize 改为 `chat-completion` / `openai-response`，重跑七项（`RUN_AGNES_LIVE=1`）。
2. 把 `protocol` 从自由字符串改为枚举：schema 用 `Literal[...]`，前端改成下拉，把"哪些协议支持助手"在保存时就暴露，而不是运行时 422。
3. 在实施记录里补一条更正：七项失败是夹具错误，不是准入逻辑或供应商问题，避免后续照着错误结论排查。

这一步必须最先做。23 个工具、四层记忆、Skill 按需加载的真实表现目前全是零证据，替身测试只能证明协议正确，证明不了模型会不会用。修完这个字符串，才有资格判断下面哪条建议更紧急。

### P0-2 把"能做什么"从正则里解放出来

不建议立刻重写授权层，先做投入产出比最高的一步：**让可执行动作可被看见和点选**。

1. 首屏引导按当前页面上下文生成可执行示例（标准页给"创建两个分镜并关联已选素材"这类真实可用句式，画布页给节点／连线句式），点击即填入输入框。数据源就是已有的授权目录（`standard_write_requests` / `canvas_write_requests`），不用新接口。
2. 当用户说了执行意图但正则未命中时，回复里明确给出"当前可执行的说法"或建议改用结构化入口，而不是无声降级成纯聊天。这一条只需在未命中处补一个提示分支。
3. 中期方向：把高价值动作做成结构化入口（输入区动作菜单／斜杠命令），用户选动作、模型只负责填参数。这与现有安全模型天然一致——服务端本来就是按"已应用真实指令 + 可信版本"校验，只是把意图来源从"猜文本"换成"用户显式选择"，正则只用做兜底。

### P1-1 让预算跟模型走

`CONTEXT_TOKENS` 改成从模型配置读取（`runtime_profile.context_window`，缺省回落到 65536），`TOOL_RESULT_TOKENS` 与 `MEDIA_TOKENS` 至少提到 Settings 层。真实模型验收时顺便记录一次实际 token 用量与估算偏差，再决定要不要接 tokenizer。

### P1-2 拆前端核心组件

按职责切三块：草稿与选择状态、运行与轨迹投影、输入与发送。目标是把 `AssistantConversationBody` 降到 150 行以内、单行不超过 120 字符，并把 `useState` 收进 `useAssistantComposer` 之类的自定义 Hook。这类纯重构风险低、收益长期，适合在真机验收之后、新功能之前的窗口做。

### P1-3 补 reconciling 的人工核实闭环

「供应商受理不明」目前会长期占预占额度，用户没有出口。最小可用版本：在成果卡上提供"我已核对供应商后台"的显式动作，按原请求身份记录人工裁决，释放或延用预占，不换幂等键、不重复外发。这是登记在案的第 3 项，建议随真机验收一起做，因为真实供应商才会大量暴露这个状态。

### P2-1 文档收敛

把"护栏"从接口文档里剥出来，单独维护一份约束清单（谁在什么边界拒绝、错误码是什么），`docs/api/assistant.md` 回到契约本身：路径、请求、响应、错误码。现在读者要读完 352 行才能确认一个接口长什么样。

### P2-2 退役节奏

V0/V1/V2 的只读展示可以长期保留，但服务端的旧写入口建议定一个明确的退役窗口。四代协议同时在跑的维护成本，随工具数量增加还会放大。

### P2-3 补一层可观测性

目前只有持久操作账本，没有聚合视图。建议按工具维度统计调用次数、失败码分布、`paused_budget`／`paused_error` 触发率、平均 tool 轮次。真机验收后，这组数据能直接回答"哪个工具模型最不会用"，比逐个补正则更有效。

## 5. 推进顺序建议

1. 修夹具 → 重跑七项真机验收（P0-1）。拿到真实失败样本再谈优化。
2. 按真机结果决定：若模型在固定句式下都难以稳定调用，优先 P0-2 的结构化入口；若调用顺畅但表达受限，优先 P0-2 的引导与提示分支。
3. 同期做 P1-3 的人工核实闭环（真实供应商场景下必要）。
4. 之后做 P1-1、P1-2 两项低风险改造，再收 P2。

## 6. 本评估的边界

- 未运行完整测试套件，未验证 183 个未提交改动的整体一致性；仅对第 3.1 节的协议取值与第 3.2 节的句式覆盖做了本地实测，其余为源码直读。
- 未调用任何真实模型、媒体供应商或 MinIO。
- 第 3.2 节的样本只有 10 条，用于说明句式边界的存在与量级，不作为授权覆盖率的统计结论。
