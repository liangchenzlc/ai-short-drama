## 一、🔴 阻塞

### CR-01 单条媒体意图异常会拖垮整个调度进程

- **表现**：`service/assistant/operations/media_settlement.py:76`、`:159` 在原生任务/生成记录/图片组缺失时抛 `RuntimeError`；调用方 `agent/coordinator/media_runtime.py:71` 只捕获 `SQLAlchemyError`，`RuntimeError` 直接穿透 `collect_media_results`。
- **影响**：`tasks/runtime/runtime.py:139-143` 把 `collect_media_results` 和其它 tick 放在同一个 `try` 里，异常跳到 `:193` 的兜底 `except Exception` 后 `sleep(1)` 重试。这一 tick 的发布、渲染、Agent 调度、记忆维护全部不执行。坏 operation 因事务回滚而 `updated_at` 不前进，`media_runtime.py:22-30` 按 `updated_at` 升序取前 100，它永远排在队首 → **所有账号的助手执行与媒体结算持续停摆**，直到人工修数据。
- **方向**：结算内把「对象丢失」翻译成带错误码的 `Conflict`/`NotFound`；`collect_media_results` 对每个 identifier 单独 `try/except Exception` 并强制推进游标（标记 `intent.status`），保证坏数据只影响自身。

### CR-02 租约失效时最终答案被静默丢弃

- **表现**：`agent/runtime/executor.py:285-294` 调用 `finish(status="succeeded", content=...)` 不检查返回值；`service/assistant/execution/run.py:280-283` 在 `lock_run` 失败或 fence 不匹配时 `return False`。
- **影响**：模型已生成完整回答，但落库被拒绝，调用方当作成功返回；Run 既没进成功也没进失败，`cleanup_run` 只清沙箱，日志无任何记录。用户看到「这次执行结束但没有回复」，只能靠 recovery 超时兜底。租约在最后一次心跳后过期、Worker 被新 fence 接管都会触发。
- **方向**：检查返回值；`False` 时记录 fence 不匹配并走可观测分支（写 `accepted_unknown` 或明确失败），不允许当成交付成功。

## 四、建议的改进顺序

**P0（先止血，不依赖重构）**

1. CR-01：结算逐条隔离 + 错误类型化 + 游标必前进。这是唯一会让「所有人都不能用」的问题。
2. CR-02：`finish` 返回值必须被消费，失败要有日志与终态。
3. CR-08：`finish_tool` 判空并转 `Conflict`，避免单条脏数据把任务永久锁死。

**P1（下一迭代，先补观测再改结构）**

4. CR-03：错误契约保留 `retryable`/`retry_after`，只对 `accepted_unknown=False` 做 Run 级有限退避重试。
5. CR-05 / CR-12 / CR-13：给 `agent_events` 冗余 `message_id`、`block_id` 列并加索引，读路径改批量查询与分页；这三项决定长会话是否可用。
6. CR-04：把事件落库改成「有界队列 + 单 writer 批量 flush」，顺带消掉共享 dict 的竞态（与上一轮已做的 `_DeltaBuffer` 合并即可，不需要新平台）。
7. CR-09 / CR-10：维护任务补兜底异常与心跳隔离；等待加到期策略（超时进入可重试或明确失败），避免永久阻塞会话。
8. CR-14 / CR-15 / CR-16 / CR-21：连接状态独立呈现、@ 提及死路兜底、版本解析统一 `safeVersion`、停止状态收敛到 task projection。

**P2（结构优化，按改动收益排序）**

9. CR-06 / CR-07 / CR-11：checkpoint 只校验新增通道并加环保护；看门狗改只读短查询 + `join(timeout)`；预览接口改只读快照，`apply` 已有 `preview_hash` 兜底。
10. CR-17 / CR-19 / CR-20：流式正文走独立订阅 + 列表虚拟化；关闭面板暂停流；分页互斥改用 ref 与请求序号。
11. CR-18：问题卡空字段降级。

**P3（随手清理）**

12. CR-22 删除或统一 `mode` 契约；CR-23/CR-24 收敛权限与状态常量；CR-25 统一时间格式化；CR-26 删死代码、提常量；CR-27 合并重复 CSS；CR-28 合并技能配对实现。

## 五、值得保留的部分

- 幂等与围栏设计扎实：消息、任务控制、批量撤销、业务工具调用都有唯一约束兜底，写入口统一先锁 Project → Conversation（`domain/assistant/**`）。
- 事件 + 快照投影的双轨模型边界清楚，前端只用 `applyTaskEvent`/`mergeTaskSnapshot` 两个入口，重连按游标补齐，而不是全量重拉。
- 停止、受理不明、访问结束三类终态有明确文案与责任划分，没有把「可能已提交」伪装成可重试。
- 测试密度高：助手相关测试文件 54 个，覆盖正式图、媒体等待、轨迹、记忆、权限与前端 Node 行为。

## 六、验证范围与限制

- 本轮为静态审查：读完上述路径源码、调用方与测试目录，用 `grep`/定点读取交叉核对每条证据；未启动服务、未连真实 MySQL/MinIO、未调用供应商、未跑浏览器与压测。
- 上一轮实测结论沿用而不重测：草稿保存 p95 约 0.7ms（故不列 CR 级问题）、单轮 128 片增量合并约 0.1ms、续租线程池排队约 294ms（未证明租约过期，故 CR-04 只按竞态与吞吐风险登记）。
- 未覆盖：MCP 工具调用端到端、沙箱真实 OpenSandbox 行为、多 Worker 并发下的 MySQL 锁竞争、真实长会话（万级事件）压测。这些场景下 CR-05、CR-07、CR-12 的实际严重程度可能高于本文估计。
- 结论中的严重级别沿用项目约定：🔴 阻塞合并、🟡 应当修复、🟢 可选建议；不代表已验证的发生概率。
