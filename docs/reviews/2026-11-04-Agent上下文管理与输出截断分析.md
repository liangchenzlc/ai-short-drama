# Agent 上下文管理与输出截断分析

日期：2026-11-04。范围：当前工作区正式 Agent Runtime、测试数据库最新会话，以及同日的 [Claude Code Harness 对照分析](2026-11-04-Claude-Code-Harness对照分析.md)。本次只分析并记录，不修改运行代码或数据库。

## 1. 核心结论

本次失败直接来自平台统一设置的 **单次输出 8192 tokens**，与累计输出预算耗尽、上下文装满均无关。最后一次 DeepSeek 请求把这 8192 tokens 全部用于思考，尚未产生正文或工具调用，就收到供应商明确的 `finish_reason=length`。网关随后抛出 `agent_response_truncated`，执行器将整个 Run 结算为失败。

建议把 token 用于模型容量管理、上下文压缩和实际用量统计；任务是否继续应由目标进展、用户停止、权限、真实等待和不可恢复故障决定。供应商原生的上下文窗口与单次输出上限仍然存在，需要通过压缩、按需读取、分段保存与继续执行处理。

## 3. 当前上下文与预算机制

| 环节 | 当前实现 | 影响 |
| --- | --- | --- |
| 模型窗口 | 未提供有效容量声明时按 65536；有效声明最大可到 1048576，但平台最多使用 262144 | 本次模型没有窗口声明，使用默认值 |
| 输入准入 | 窗口减去单次输出、4096 工具余量、2048 安全余量 | 本次可用输入为 51200 |
| token 估算 | JSON UTF-8 字节数约除以 3，媒体另计预留 | 属于平台估算，不是供应商 tokenizer；本次估算高于实际报告 |
| 规范目标 | 原始目标、最新更正、已消费回答投影到 pinned Human；总计约 12 KiB，单条正文最多先取 8000 字节 | 原文仍在持久消息中；投影可能省略较长要求，需精确回读 |
| 工作笔记 | 成功读取及来源校验后记录；最多 32 条、约 3000 tokens | 超额会从活动工作集移除最早项并记录省略数 |
| Skill | 最多 8 个活动方法，正文合计约 8000 tokens；活动正文及完整工具调用组保留 | 有助于防遗忘，也使固定上下文成本增加 |
| 工具选择 | selector 先选工具，固定工具和活动 Skill 依赖再补入 | 摘要在真实工具池确定后执行；本 Run 每轮有一次额外 selector 调用 |
| 自动摘要 | 对非 pinned 历史调用官方摘要；触发值为固定成本加剩余可用空间的 70%，保留值默认加 25% | 已具备自动压缩，不需要重新建设一套摘要器 |
| 摘要辅助模型 | 按窗口连续分批，前一摘要合入下一批；保留来源、方法、资源与游标标记 | 可处理长历史，但摘要调用自身仍可能失败 |
| 大文本工具结果 | 通用结果边界尚无自动转成预览与可回读引用的机制 | 已有部分读取工具分页，不能覆盖任意工具的大结果 |
| 最终守卫 | 固定内容过大、摘要后仍超限、实际出站 body 超限会抛 `agent_context_budget_exhausted` | 目前恢复手段不足，异常最终会结束 Run |
| 单次输出 | 主模型默认固定 8192，并下发给 SDK；selector 和 summary 也复用模型默认值 | 未依据模型原生输出能力及调用角色区分；直接触发本次故障 |
| 累计执行额度 | 每 Run 默认 240 次模型请求、200 万输出 tokens；helper 与子任务计入父 Run | 达限会暂停，需要用户继续；与本次故障无关 |

DeepSeek 历史 `reasoning_content` 已在真实 SDK 出站和上下文引用计量中保留。不能为了缩短请求随意删字段，必须遵循对应供应商协议并保持完整工具调用组。

## 4. 对原对照文档的补充核对

“先卸载，再摘要”的方向适用。原文提出直接用现有工具回读大结果，当前代码尚缺两个前置条件：

1. `read_operation_receipt` 目前返回操作状态、成果引用与撤销收据，没有原始任意工具结果正文，也没有正文分页参数。
2. `read_task_results` 虽有正文分页，但只接受 `apply_standard_patch` / `apply_canvas_patch` 的原始保存操作，不能读取任意读取、Skill 或沙箱工具结果。

因此不能先把 ToolMessage 缩成 operation ID 就算完成卸载。应先补齐受当前 scope、来源撤回和方法资格约束的原结果分页读取，再接入统一卸载。可扩展已有回读工具并复用 Operation，是否需要其他存储取决于具体结果类型，无需先引入新表。

原文对输入硬拒绝的讨论没有覆盖本次单次输出被思考占满的情况；仅实现大结果卸载和摘要，仍不能解决本次问题。另外，原文对照对象是教程仓库，不能据此推断商业 Claude Code 的完整内部实现。

## 5. 建议的改造顺序

### 第一项：先处理固定单次输出与已确认截断

将输入窗口、模型原生最大输出、调用角色所需输出分别表达。主模型依据已核验的模型能力设置可用单次输出空间，同时为输入保留足够窗口；selector 使用短结构化输出，summary 使用独立摘要输出配置。不能在没有能力证据时统一改成某个更大的数字，也不能只删除请求中的 `max_tokens`，因为供应商默认值仍可能很小。

单次输出设置目前还参与预算校验、出站预占和摘要窗口计算，修改时需同时调整这几处，让同一次调用使用一致的实际输出预留。

对已确认的 `length/max_tokens`，返回带通道和可恢复信息的结果，交由执行层恢复：

| 截断位置 | 恢复方式 |
| --- | --- |
| 只有思考，没有正文或工具参数（本次情况） | 在原模型能力允许时增加单次可用输出；结合已支持的思考配置重新生成。新请求从原目标和真实成果继续，不把残缺思考当作可执行成果，也不承诺接续供应商内部思考 |
| 长正文中断 | 以已持久保存的正文段、版本和未完成范围继续生成；最终组合交付。不能只在聊天内丢一句“继续”，却没有保存位置和去重依据 |
| 工具参数中断 | 不执行残缺调用，不拼接两个请求中的半段 JSON；下一轮生成更小且完整的工具调用 |
| 已达到模型原生极限且无法推进 | 保留任务与已保存成果，报告具体阻碍，允许用户继续或换模型；不提示用户笼统“缩小创作范围” |

恢复过程中保留每次真实模型调用和实际费用事实，避免重新执行已成功的业务写入。持续相同状态且没有新增正文、有效工具动作或成果时，再按无进展处理，避免无限重新生成。

这类恢复针对供应商已明确结束的响应。响应空闲 120 秒后直接报错、受理不明不自动重发的既定规则继续有效，不能混入连接超时重试器。

### 第二项：将累计 token 额度从任务停止条件改为观测

累计输入、输出、缓存命中与费用继续统计。累计 token 达到提醒线时发出用量信息，不自动把正常推进中的创作任务判为失败或要求手动续期。

调用次数和 LangGraph 递归保护需一起检查：当前 `ModelCallLimitMiddleware` 与 `recursion_limit` 都绑定冻结调用预算。若目标是持续运行，批次调度应通过 checkpoint 交接后自动继续，不能只去掉账本校验却保留另一个固定出口。用于识别失控的条件应基于重复错误和无进展，与正常长任务区分。

### 第三项：补齐大工具结果卸载与精确回读

完整结果先持久保存，模型上下文仅保留简短预览、操作身份、内容版本或 checksum、总长度和下一段游标。原结果读取沿当前授权与来源资格执行；活动方法正文仍遵循方法加载与释放规则。

统一在进入后续模型上下文之前处理体积，保留完整 assistant/tool 协议配对。分页读回也需要占用活动窗口并随旧历史压缩，不能把每次读回的全文持续叠加。

### 第四项：在现有摘要上补恢复链路与任务续点

保留现有摘要器、source/Skill 资格撤回和可信业务收据。增加“卸载大结果 → 收缩可重读旧内容 → 摘要 → 重算真实包络”的顺序，让正常上下文增长优先通过重组恢复。

任务续点应能表达当前目标、已保存成果身份、已回答问题、未完成项和必要读取游标；成果完成状态仍以业务收据为准。已有 pinned 目标、工作笔记与收据目录可继续复用，避免新增另一套成果事实源。需要完整原文时根据来源身份精确回读。

确实连固定策略、必要工具 schema 与最小目标都装不进模型窗口时，才返回准确的容量错误；不能静默截掉用户约束或工具协议。

### 第五项：让用户看见恢复状态

输出接续和上下文压缩各显示对应状态，例如“正在继续生成”“正在整理上下文”，都不提前显示失败。界面预览截取继续明确标记，避免与实际输出中断混为一谈。

最终无法恢复时给出具体原因，并保留当前任务、真实成果和模型选择能力。仅接到正常停止原因且得到完整可交付结果后，才结束本轮交付。

## 6. 改造后的集中验证重点

1. 用真实网关与图执行的受控响应重现“8192 reasoning、正文为空、length”，验证自动恢复后可产生正文或有效工具动作。
2. 验证正文截断可接续、残缺工具 JSON 不执行、恢复后不重复成功写入；实际用量分别记账。
3. 验证长材料卸载后逐段回读 checksum 一致；上下文压缩后仍保留目标、回答、成果身份和精确游标。
4. 验证累计 token 达提醒线时正常任务继续，重复无进展会明确暂停；checkpoint 恢复仍沿正确作用域和来源资格执行。
5. 验证响应超时与受理不明仍按既定规则停止；前端分别显示预览截取、上下文整理和继续生成。

每项实现期间只做基本检查，全部完成后集中跑上述回归。真实供应商的最大输出、思考配置与接续行为需单独验证，不能用受控响应测试代替。
