# 当前项目代码审查（2026-09-20）

## 结论与范围

本轮确认 8 项正确性、可靠性或性能问题，另有 1 项条件性密钥使用风险。优先处理生成结果丢失、任务恢复和编辑内容覆盖。以下优先级为修复排序，不代表安全漏洞等级：P2 为应安排修复的问题，P3 为规模增长前的优化。

审查覆盖 FastAPI 暴露的接口、配置与密钥处理、模型发现和调用、任务发布/执行/恢复、MinIO 归档与资产采用，以及前端配置、任务、资产库和本地项目编辑路径。采用离线静态调用链检查，并由独立审查交叉核对；未运行应用、攻击验证、测试套件或真实模型调用，未读取真实密钥、连接云数据库或改变运行中的服务。

这是重点路径审查，不是所有文件、依赖和部署环境的全面安全认证。Codex Security 扫描启动工具执行失败，未返回扫描 ID，因此没有完成该工具的正式报告流程。本文件是人工源码审查记录。

路径均相对项目根目录，行号对应审查时版本。

## 1. P2：收到流式结束事件后，仍等待 HTTP 响应结束，可能丢失完整文本

- 位置：`backend/src/short_drama/ai/transport.py:124–140`；`backend/src/short_drama/ai/gateway.py:89–125`；`backend/src/short_drama/ai/streaming.py:23–25,39–50`。
- 触发：中转站已经发送合法的 `[DONE]` 或 `response.completed`，但未及时结束 HTTP 响应；或终止事件之后连接异常断开。
- 原因：传输层先把响应读到 EOF，返回后才调用 SSE 解析器。解析器虽然认识终止事件，却无法让传输层停止读取。后续读取超时或异常会使整个调用失败，已收到的结果没有交给持久化层。
- 影响：上游可能已经成功并计费，任务仍报 timeout/transport_error，正文丢失。仅延长超时不能解决这一条件下的问题。
- 建议：传输时增量解析 SSE，验证协议终止事件后完成结果并主动释放连接；在合法终止前断流时，单独保留已收到的部分正文和失败证据，不把部分正文标为成功，也不自动重发收费请求。
- 验证建议：离线模拟完整终止事件后持续保持响应开启、以及终止事件后抛出读取异常。前者应及时结束，后者不应丢失已确认的完整正文；缺失终止事件仍应失败。
- 限制：源码确认了该条件路径；没有证明它就是此前某一笔真实 timeout 的原因。

## 2. P2：总超时无法打断正在阻塞的读取，实际耗时可超过预算

- 位置：`backend/src/short_drama/ai/transport.py:113–131`。
- 触发：请求开始时读取超时设为 3600 秒，上游在接近任务截止时间时返回一块数据，下一次读取再长时间停顿。
- 原因：每次 `read1()` 之前检查截止时间，但 socket 的读取超时仍沿用请求开始时的值，没有按剩余预算缩短。下一次阻塞期间无法再次执行时间检查。
- 依据：本地安装的 urllib3 `util/timeout.py:96–103` 明确说明 read/total 不是整个响应的绝对截止时间；`connectionpool.py:523–540` 在获取响应前设置连接读取超时。
- 影响：声明的一小时不是可靠的硬上限；线程可能继续被占用，并超过按一小时任务设计的 RabbitMQ ACK 时间窗口。DNS 和解压耗时也未在本轮验证为严格可中断。
- 建议：让每次阻塞操作服从当前剩余预算，或采用具有真正总截止时间及取消能力的传输机制；明确区分总预算、连接超时和流空闲超时。
- 验证建议：用可控时钟和分块响应模拟截止前返回数据后停顿，验证总预算耗尽时能终止；不必真实等待一小时。

## 3. P2：有供应商任务 ID 的超时任务，缺少查询原结果的恢复入口

- 位置：`backend/src/short_drama/service/generation_execution_service.py:214–241,302–310`；`backend/src/short_drama/dao/task_runtime_dao.py:53–60`；`backend/src/short_drama/service/ai_generation_service.py:52–85,379–387`；`backend/src/short_drama/tasks/recovery.py:22–28`。
- 触发：异步视频任务已被供应商接受且获得 `provider_task_id`，到达等待预算时供应商仍在运行，或最后一次查询发生网络错误。
- 原因：任务被置为 failed 并清除后续调度动作，调用记录仍是 sent。普通重试禁止 sent/unknown；恢复只允许已成功媒体归档，或 `message_delivery_unknown`，不允许此类 generation_timeout/查询错误继续 poll。后台恢复也排除终态任务。
- 影响：即使供应商稍后成功，本系统没有公开恢复路径把结果拉回资产库。用户需要供应商后台或人工运维处理，可能再次付费生成。
- 建议：保持失败状态的语义，提供明确的“查询原任务结果”操作。仅用已有供应商任务 ID 发 GET，不重发生成 POST；设置独立的查询恢复窗口和凭据保留规则，并在成功后执行原归档流程。不要仅放开按钮却继续沿用已经耗尽的生成预算。
- 验证建议：任务超时后模拟供应商转为成功；恢复过程中生成 POST 次数保持为 1，并且同一输出只产生一个资产。
- 说明：停止无限自动轮询本身合理；缺陷在于安全的人工取回入口也被关闭。无需恢复之前删掉的 task unknown 状态。

## 4. P2：视频归档完整缓存在内存，允许尺寸与并发组合过大

- 位置：`backend/src/short_drama/service/generation_archive.py:19,135,161–163`；`backend/src/short_drama/ai/transport.py:124–140`；`backend/scripts/start_generation.ps1:28–30`。
- 触发：归档大体积视频，尤其是默认两个视频工作线程同时下载。
- 原因：单视频允许 1 GiB，下载先累计 bytearray，再转换为 bytes；转换时原缓冲区和结果同时存在。上传又使用内存流，整个流程没有磁盘暂存或分块转存。
- 影响：单次大文件转换就可能短时占用约两份文件大小的内存，并发会进一步放大。在小内存机器上有进程被终止的风险，影响同进程其他任务；本轮没有进行实际峰值内存测试。
- 建议：边下载边限流、计数和计算 hash，暂存到受限临时文件，再上传 MinIO；约束并发和暂存总量，处理失败与取消后的清理。保留现有地址校验、尺寸上限和校验和命名。
- 验证建议：使用本地生成的大文件流验证峰值内存不会随完整文件尺寸线性翻倍，下载中断后没有错误资产记录。

## 5. P2：两个标签编辑同一分集，会静默覆盖已经保存的内容

- 位置：`frontend/src/pages/projects/EpisodePage.tsx:42–48`；`frontend/src/features/projects/episode-workflow.ts:833–843`。
- 触发：两个标签打开同一分集。A 修改剧本并显示已自动保存；B 随后修改素材或分镜。
- 原因：B 从自己内存中的旧 workflow 快照计算新值，然后整份写入同一 localStorage key。没有保存版本比较或并发冲突处理。
- 影响：A 的剧本被 B 的旧值覆盖，双方仍显示保存成功；刷新后才发现丢失。这里影响的是当前本地演示编辑器，不是服务端资产采用事务。
- 建议：保存带版本并在冲突时阻止静默覆盖；跨标签监听仅用于提示和刷新，不能单独保证并发写安全。需要可靠原子更新时采用 IndexedDB 事务，或随编辑器接入后端使用版本控制。
- 验证建议：两个独立标签按上述顺序修改不同字段；应保留两者修改，或明确提示冲突且保留待提交内容。

## 6. P2：部分本地存储异常未捕获，会丢失表单并打断工作区

- 位置：`frontend/src/pages/assets/AssetsPage.tsx:33–35,86–88`；`frontend/src/features/projects/ProjectOverview.tsx:38–42`；`frontend/src/main.tsx:12`；`frontend/src/data/demo.ts:17–18`。
- 触发：localStorage 配额满、浏览器存储被禁用，或持久化发生其他异常。
- 原因：素材新增先更新状态并关闭表单，再在 effect 中直接写入；项目详情也有未捕获写入；启动时 seedDemo 在 React 渲染前直接读取存储。当前 App 没有对应错误边界。
- 影响：新增数据未保存且表单已经关闭；effect/渲染异常可能使工作区卸载。启动初始化异常会连服务端 AI 配置和任务页面一起阻断。
- 建议：持久化成功后再关闭表单并提示成功；统一处理存储错误、保留未保存内容；演示初始化失败不阻止服务端页面启动。错误边界作为最后保护，不能替代保存结果检查。
- 验证建议：令存储读/写分别抛出异常，验证 UI 仍可使用、内容保留、失败提示准确，服务端页面能打开。
- 反证：分集 saveWorkflow 和部分项目创建入口已有异常处理，不是全项目都缺少处理。

## 7. P2：自定义 RabbitMQ 队列命名空间与启动脚本不一致

- 位置：`backend/src/short_drama/tasks/celery_app.py:11–18,42`；`backend/scripts/start_generation.ps1:29–30`；`backend/README.md:68`。
- 触发：把 `GENERATION_QUEUE_NAMESPACE` 从默认 short_drama 改为其他值，再用当前脚本或手动示例启动 Worker。
- 原因：生产者/拓扑使用 `{namespace}.tasks.ai.{kind}`，Worker 的 `-Q` 固定为 `tasks.ai.{kind}`，且禁止自动创建缺失队列。
- 影响：Worker 可能直接因未知队列启动失败；即使另行存在旧队列，也不能消费发布到新命名空间的消息。默认配置不受影响。
- 建议：启动入口从同一 Settings/topology 推导订阅队列；部署说明中的 RabbitMQ 文本 ACK 超时策略也同步匹配实际队列名。
- 验证建议：使用非默认命名空间进行不连接 broker 的配置契约检查，确保发布目标、声明队列、Worker 订阅和策略匹配一致。

## 8. P3：编辑剧本会重复枚举整个浏览器媒体库，预览 URL 也未释放

- 位置：`frontend/src/features/projects/episode-workflow.ts:232–250`；`frontend/src/pages/projects/EpisodePage.tsx:32–37`；`frontend/src/features/projects/episode-media.ts:4,20–30,57`。
- 触发：已有大量本地图片/视频时持续编辑剧本，或切换多个项目。
- 原因：每次编辑重建 assets/shots 数组，触发两次 listUsableMedia；每次都 getAll 取全库含 Blob 的记录，再筛选当前项目和类型。effect 清理只丢弃结果，不取消读取。全局对象 URL Map 没有 revoke/释放路径。
- 影响：随媒体规模增长产生不必要的查询、对象创建与 Blob 引用保留。静态证据不能证明一定发生 OOM或某个具体卡顿时长。
- 建议：按项目和媒体类型建立索引，列表取元数据，预览按需取 Blob；只在媒体变化时刷新，管理对象 URL 生命周期。
- 验证建议：编辑正文不触发全库读取；项目切换后不再使用的对象 URL 被释放。

## 条件性安全设计风险：更换服务地址仍沿用旧 API Key

位置：`backend/src/short_drama/service/ai_model_config_service.py:92,141–161`；`frontend/src/api/modules/ai-model-configs.ts:16–17`。

把已有配置从服务 A 改到服务 B，密钥留空时前端省略 apikey，后端保留旧密钥。保存后的模型发现只与当前已保存地址比较，因此旧密钥会发送到 B；后续生成同样如此。如果 B 是不可信中转站，操作者可能意外泄露 A 的密钥。

这是源码可确认的行为，但 UI/文档本来就声明“留空保留原密钥”，且当前同一操作者同时控制地址和密钥。因此不能据此声称存在无交互远程盗密钥或权限绕过。建议跨 origin 修改时要求重新输入或清除密钥，至少明确提示旧密钥将发送到新主机；同源路径修改不必一律重填。

## 已检查的控制及审查限制

- 已审路径使用 SQLAlchemy 参数绑定；未确认 SQL 注入。模型密钥响应有脱敏，校验错误不返回原始秘密输入；未确认直接密钥回传。
- 模型发现和生成有 DNS/IP 校验及固定连接地址，下载逐跳检查且不携带模型认证头；未确认任意 SSRF。显式受信主机白名单属于部署者授权，不等同于自动发现的漏洞。
- 任务有消息版本、租约和调用证据；不能把 sent/unknown 任务直接改为自动重发。资产采用有显式确认及预期媒体检查。
- 默认启动绑定 loopback，文档明确当前单用户且无认证。若改变为多人或公网部署，需要新的身份权限设计；本轮未验证实际网络暴露面，也未把缺少认证直接认定为当前可利用漏洞。
- 未验证云 MySQL/RabbitMQ/MinIO 的 TLS、账户权限、防火墙、备份及在线策略；没有运行依赖漏洞库扫描、压力测试或真实 exploit。
- 不把本地演示编辑器尚未全部接入后端、视频仅识别容器头等已明确标注的范围限制伪装为新发现的攻击漏洞。

建议修复顺序：先处理 1、2、3 的生成结果与等待边界，再处理 5、6 的数据保存，随后处理 4、7；8 按媒体规模推进。跨服务地址的密钥处理可与配置表单改进一并修复。
