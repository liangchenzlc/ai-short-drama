# 目录与职责维护

采用“顶层职责 → 业务模块 → 具体能力”的目录组织。目录是查找入口，文件按会独立变化的职责划分；行数只提示复审，不把同一事务或状态机机械切碎。

## 前端

```text
frontend/src/
├─ app/{router,providers,layouts/studio,styles}/
├─ pages/
│  ├─ projects/{list,workspace}/index.tsx
│  ├─ creation/
│  │  ├─ index.tsx
│  │  └─ {script,assets,storyboard,assembly}/index.tsx
│  ├─ identity/{login,register,verify-email,reset-password,account}/
│  └─ {ai-config,skills,media-library,not-found}/
├─ features/
│  ├─ creation/
│  │  ├─ workspace/{layout,navigation,model,styles}/
│  │  ├─ writing/{editor,story-settings,rewrite,sessions}/
│  │  ├─ assets/{list,editor,images,extraction,sessions}/
│  │  ├─ storyboard/{list,editor,images,videos,references,history,sessions,workbench}/
│  │  ├─ sound/{tracks,voices}/
│  │  ├─ assembly/{workbench,timeline,player,inspector,materials,subtitles,export,sessions}/
│  │  └─ shared/{sessions,recovery,feedback,resource-view,references,model,generation,media,styles}/
│  ├─ assistant/{panel,conversations,composer,attachments,references,skills,messages,operations,history,runtime,recovery}/
│  ├─ projects/{list,creation,management}/
│  ├─ identity/{session,forms,account,storage}/
│  ├─ generations/{tasks,batches,presentation}/
│  ├─ ai-config/{catalog,editor,selection,preferences,testing}/
│  ├─ skills/{library,imports,details,resources}/
│  ├─ media/{library,selection,image-groups,image-tools}/
│  ├─ canvas-integration/{launch,archives}/
│  └─ shared/async/
├─ api/<业务>/<功能>.ts
├─ types/<业务>/<功能>/
├─ shared/{ui,async,navigation,media}/
└─ integrations/canvas/{assistant,contracts,session,image-tools}/
```

页面目录的 index.tsx 组合业务组件；存在页面样式时使用同目录 index.css，没有独立样式时不创建空 CSS。功能目录中的组件按职责命名。纯函数、Hook 与复杂子组件就近放到具体能力目录；具名类型统一放 types 对应路径。类型层不能反向引用功能实现；HTTP DTO 保留服务端字段及字符串 ID／版本。

分镜工作台组合操作与视图，列表／离页详情／本机草稿交给 useStoryboardCollection，移动删除交给 shot-mutations，信息表单交给 ShotInformation。助手会话视图、输入状态、发送载荷准备、消息渲染分别由 conversations、composer、messages 承担。受理不明时固定原载荷和幂等键，拆分不能把核对变成新发送。

分镜工具栏与共用菜单在 workbench/views，Props 在 types/creation/storyboard/workbench/views；切换前保存、锁、版本围栏及离页屏障留在工作台同一编辑生命周期，视图不另建状态副本。

## 后端

```text
backend/src/short_drama/
├─ api/
│  ├─ v1/<业务>/<功能>/
│  └─ dependencies/<业务>/
├─ schemas/<业务>/<功能>/
├─ service/<业务>/<功能>/
├─ dao/<业务>/<功能>/
├─ domain/<业务>/<功能>/
├─ ai/{adapters,gateway,prompts}/
├─ agent/
│  ├─ harness/
│  ├─ runtime/decisions/
│  ├─ gateway/
│  └─ {context,resources,tools,task,memory,skill,native,session}/
├─ tasks/{assistant,generations,canvas,identity,rendering,runtime}/
├─ db/{access,scope}/
└─ {core,storage,utils}/
```

各层业务目录采用 identity、projects、creation、assistant、generations、ai_config、skills、media、canvas、system；只为实际职责创建目录。creation 再按 writing、assets、storyboard、sound、assembly、drafts 分组。复杂 Service 在功能包内拆受理、查询、执行、结算与归档；同一事务共享 Base／Session，组合入口负责完整提交边界。

例如 generations/execution 按 provider、archive、settlement 拆分，generations/admission 保留幂等受理和任务落库事务；assistant/tasks 按任务生命周期分工；creation/assembly/document 按文档及片段操作划分；db/access 将查询限制、写入守卫与账号上下文分开。测试替身应补丁到真实实现模块的绑定处。

## 搬迁与退役查询

[源码迁移映射](../data/2026-10-28-源码迁移映射.json)登记旧文件到当前实现的对应关系，支持一对多。它用于评审定位及删除路径的测试选择，不是运行时兼容层；业务测试归属仍由 test-map.json 决定。

| 原入口／职责 | 当前归属 |
| --- | --- |
| projects 页面与 episode 阶段页 | pages/projects、pages/creation，业务进入 features/creation |
| api/modules、api/types | api、types 各自按业务／功能管理 |
| components、lib 的通用部分 | shared；有业务语义的部分回到相应 feature |
| ai-assistant、agents 的现行助手功能 | features/assistant；画布使用 integrations/canvas 入口 |
| 平铺的写作、素材、分镜、成片模块 | 后端各层 creation 下的 writing、assets、storyboard、assembly |
| 平铺的 Agent 会话、运行、任务与成果 Service | assistant 下的 conversations、execution、tasks、artifacts 等 |
| scope 0–2 专属入口、小说／大纲／改编链、演示 workflow | 删除实现与专属测试；共享且仍有效的行为测试迁至现行链 |

有效 V3 控制链、Harness 复用的 RuntimeStore、私有候选与明确采用继续维护。协议中 episode 等字段及数据库历史范围字段不随宿主命名盲目重命名。退役表与获准测试数据清理见[数据库增量](../database/migrations/2026-10-28-source-restructure/README.md)。

## 以后怎么新增

先找页面及业务能力，再确定具体职责；不要往模块根不断追加平铺文件。新增类型进 types，新请求进 api，纯 UI 才进 shared。只有事务、状态机或协议顺序必须共同理解时保留同文件，并在关键边界用中文注释说明原因。

改动后预览测试影响、运行对应级别验证，再执行 check-docs 与 check-quality。路径移动必须同步调用者、测试、文档和迁移映射，不能忽略整棵目录绕过门禁。
