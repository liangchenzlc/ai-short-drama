# 代码质量规范

> 适用范围：`backend/src`、`frontend/src`。判定工具是 `scripts/check-quality.mjs`，本文说明判定依据与取舍；目录结构与命名见[前端手册](../../frontend/AGENTS.md)与[后端手册](../../backend/AGENTS.md)。

## 一、优先级

**可读性与可维护性 > 正确性 > 性能 > 代码长度。**

代码主要是写给人读、给人改的，机器执行是副产品。这条优先级直接推出两件事：

- **行数不是目标**。把 800 行拆成 8 个 100 行的浅文件，读的人要在 8 个文件之间跳转才能拼出一个概念，可读性反而变差。
- **拆分的依据是职责与依赖，不是数字**。判断标准是"这里是否混了两种会分别变化的东西"，不是"这里超过 X 行"。

## 二、复杂度的定义

**复杂度 = 依赖项 + 晦涩度**。依赖项越多，改动要考虑的接口越多；晦涩度越高，读者越难在脑中还原行为。

需要警惕的三个症状，按严重程度排列：

| 症状 | 表现 |
| --- | --- |
| 变更放大 | 一个小改动要在多处同步修改 |
| 认知负荷 | 完成一次改动需要先装进太多上下文 |
| 未知的未知 | 不清楚要改哪些代码，改完也不知道影响面 —— 最糟糕 |

缓解策略只有三条，没有捷径：

1. **对增量复杂度零容忍**：这一处先加个 if 看似省事，累积三次就成了 if 链。
2. **预先投入设计**：动手前想清楚职责边界与依赖方向，比事后拆便宜。
3. **避免战术捷径**：绕过分层、复制粘贴、临时开关，都会变成下一轮的债。

## 三、模块化原则

| 原则 | 含义 | 在本仓库的表现 |
| --- | --- | --- |
| 深模块 | 简单接口，强大功能 | 对外只暴露少数函数，把复杂性关在里面，例如权限模块对外只有 `require_project`、`guard_writes` |
| 信息隐藏 | 设计决策封装在内部 | 调用方不需要知道表名映射、版本校验细节 |
| 通用设计 | 对抗过度专业化 | 同一件事只做一套实现，不为单点场景复制一份 |
| 避免类病 | 更多类、更多组件 ≠ 更好的设计 | 拆出只被调用一次、只做一行的类，是负担不是设计 |

**因此本规范不设行数红线。** 文件大小只作为复审信号：超过审视线时，问三个问题——是否混了多种职责、依赖是否过多、别人读它要不要先读别的东西。三个都否，就让它大着。

## 四、代码异味

主动识别并标记，发现时按"说明 + 方向"两段反馈：

- **重复逻辑**：同一段判断或转换出现在两处以上，改一处必然漏另一处。
- **过度耦合或循环依赖**：模块之间互相引用，改动会互相牵连。
- **脆弱设计**：一处变更会破坏不相关的部分，说明接口没有隔离变化。
- **意图不明**：命名模糊、抽象混乱，读者要猜。
- **没有收益的过度工程**：为不可能发生的场景加抽象、加配置。

反馈格式：先一句话说清问题，再给 1~2 个重构方向并说明优缺点，不要只丢结论。

## 五、错误处理

1. **把错误设计掉**：能用类型、状态、默认值表达的，不要抛异常。例如"可能不存在"的查询返回 `None`，而不是抛错。
2. **在低层屏蔽、在高层决策**：DAO、存储层把驱动异常转成业务异常，上层只处理业务语义。
3. **用通用处理器聚合**：同类错误在一个地方映射为统一响应，不在每个路由重复 `try/except`。
4. **罕见且不可恢复的错误直接失败**：配置缺失、结构不一致就该拒绝启动，不要带着坏状态继续跑。

具体到本仓库：`core/exceptions.py` 的 `BusinessError` 家族是唯一出口，`WorkflowError(code, message, status_code, details)` 承载稳定错误码；日志用模块级 `logger`，异常路径必须带上下文。

## 六、两级门禁

### 硬门禁：失败即不可提交

| 检查 | 判定 | 为什么是硬性 |
| --- | --- | --- |
| 绝对禁令 | `print`、`console`、`any`、`@ts-ignore`、`# type: ignore`、`TODO/FIXME`、`http.ts` 外引 axios | 全部可机械判定，没有"看情况"的余地 |
| 循环依赖 | 依赖图强连通分量必须为空 | 循环依赖是脆弱设计的确证，没有合理例外 |
| 跨层反向依赖 | `api → dao`、`api → domain`、`dao → service`、`service → api`、`api → features`、`components → api` | 依赖方向单向是可维护性的前提 |

### 软信号：只提示，不阻塞

- **规模**：文件超过 600 行、类超过 500 行、函数超过 100 行、参数超过 8 个、单文件 `useState` 超过 15 个，列出来供复审。
- **增长**：文件比上次基线更长时提示，用来发现增量复杂度。

软信号刻意不失败：体积由模块与范式决定，Python 的路由聚合文件和 TypeScript 的表单组件，合理体积本来就不一样。

### 存量与棘轮

`scripts/quality-baseline.json` 记录结构债务及规模信号。2026-10-22 整改消除了原有 16 处反向依赖，结构基线清空。规则：新增即失败，修好后跑 `--update` 收紧；同一文件同一规则的计数也不能增长，循环依赖不能加入基线。要放宽其他规则必须手工改 JSON 并在提交信息里说明理由。

Python 依赖由 `scripts/check_quality_python.py` 的 AST 解析，覆盖绝对、相对及函数内导入；TypeScript 依赖由编译器 AST 和模块解析检查，覆盖 import、类型导入、re-export 与动态 import。类型导入仍计入结构依赖。`print`、TypeScript `any` 和 `console` 以语法节点判定，注释和字符串不会被当作调用；忽略指令及待办标记仍按行检查。规模仍只提示，不以文件长度替代职责审查。

门禁使用后端 `.venv` 的 Python，缺省回退 `uv run python`；TypeScript 使用前端已安装的依赖。新增检测用例运行 `node --test scripts/tests/check-quality.test.mjs`，常规检查运行 `node scripts/check-quality.mjs`，`--report` 用于查看规模与依赖诊断，`--update` 仅在禁令和新增结构问题均为空时写基线。

## 七、代码审查

结构问题由 `node scripts/check-quality.mjs` 判定；语义问题**统一由 code-review-skill 执行**，不用自由发挥的方式审。

- **触发**：说"用 code-review-skill 审查 <范围>"。大改动先跑该技能自带的 `pr-analyzer.py` 做复杂度分诊。
- **四阶段固定**：范围确认 → 设计层（职责、依赖、测试策略）→ 逐行（逻辑、安全、N+1、并发、错误处理）→ 结论。
- **分级固定**：🔴 阻塞合并、🟡 应当修复、🟢 可选建议，可附 🎉 正面结论。不分级的意见等于没有优先级。
- **按语言加载**：本项目用它的 fastapi、python、react、typescript 指南，加 cross-cutting 下的 N+1、错误处理、并发三份。
- **结论要能落地**：每条 🔴/🟡 必须给出修改方向；🟢 可以只提一句。
- **审查发现的问题就地修或开计划**，不在本文件登记清单——规则文件只放判定标准，不放待办。

## 八、评审清单

- 这次改动是否让某个概念需要跨更多文件才能理解？若是，考虑合并而不是继续拆。
- 是否出现同一判断或转换的第二份实现？
- 是否新增了反向依赖或循环引用？
- 错误是在低层被翻译，还是被吞掉？
- 新代码是否比相邻代码更"聪明"？若是，改成更笨但更直白的写法。
- 修 bug 是否先有复现测试？新功能的异常路径是否覆盖？
- 改动能否用一句话说清？说不清就是职责没切干净。

## 九、大文件怎么拆

拆分的唯一依据是**变化轴**：一个文件只承载一类会独立变化的东西。判断只需问一句——下次加一个同类能力时，要改几处？只改一处（通常是加一条数据）就是对的；要改三处以上，说明分派点没有收敛。

三类常见病灶与对应拆法：

| 病灶 | 症状 | 拆法 |
| --- | --- | --- |
| 分派链 | 同一函数里连续 `if x.name == "..."`，或按类型堆 `elif` | 改成 `{名称: 处理函数}` 注册表，新增只加一行 |
| 校验流水线 | 一个函数里十几个 `if not ...: raise`，且顺序敏感 | 拆成有名字的步骤函数（`_check_run`、`_check_subject`），主函数只做编排 |
| 类承担多条生命周期 | 同一个类既持久化、又管租约、又算预算 | 按动词切分，一个类只负责一条生命周期 |

审批线用来判断，不用来卡通过率：

- 圈复杂度超过 20 要在评审里说明为什么这次不拆，超过 30 必须拆。
- 单个函数内对同一变量的字面量分派达到 6 个，必须改成表。
- 单类方法数超过 12，先确认是不是混了两条生命周期。

包级示例（`agent/`）：`tools.py` 的 `_execute` 是典型分派链，应收敛为注册表并按工具族拆 handler；`assistant_tools.py` 的 `prepare_decision` 属校验流水线，拆成步骤函数；`runtime.py` 的 `AgentRuntimeStore` 同时管 claim、lease 与结果落库，按动词切分。

拆的时候保持包级出口不变：`__init__.py` 继续导出原有符号，调用方零改动；一次只处理一个病灶，搬完立刻跑该包相关测试。
