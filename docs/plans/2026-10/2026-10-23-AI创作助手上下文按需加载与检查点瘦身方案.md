# AI 创作助手上下文按需加载与检查点瘦身方案

状态：草案。日期：2026-10-23。本轮完成代码审查、只读数据库核验和方案设计，未修改业务代码、配置或数据库数据。

## 结论

用户描述的图片进入模型历史、checkpoint 膨胀及状态查询排序故障有代码和本机数据库证据。问题跨越三个不同边界，必须分别处理：

1. **状态读取**：列表只需展示投影，却把恢复执行所需的大 JSON 一起查询和排序。这是本次会话打不开的直接触发点。
2. **持久化**：已展开的图片同时进入 checkpoint、冻结输入、实际 HTTP 请求和规范化响应；只清理 checkpoint 会遗漏另外三份。
3. **模型上下文**：历史素材持续可用，不必等于每个决策段自动携带所有素材的完整内容。持久化引用化本身不会减少发送给模型的图片，也不能直接承诺节省费用。

建议按“查询止血 → 全链路媒体引用化 → 有界的上下文按需装配”实施。暂不拆 checkpoint 表、不引入压缩、向量库或通用缓存框架。

现有 [B 方案](2026-10-23-AI创作助手素材与消息交互统一方案.md)的用户体验继续保留：素材随消息展示、发送后输入区清空、后续能继续讨论旧图。优化的是后台如何保存和读取，不能退化为要求用户反复上传或重新管理任务引用。

## 审查范围与实测证据

按 `code-review-skill` 执行范围确认、设计层审查、逐行核查和结论。范围包括共享助手输入和画布宿主、消息/任务快照、附件处理、Skill 激活与资料读取、主体/图片读取、上下文预算与压缩、模型网关、Run/Turn 持久化、状态投影和异常映射。代码索引存在旧模块路径，后续以当前工作区源码为准。

本机数据库只读事务核验：MySQL **8.4.11**，`sort_buffer_size=262144`；当时有 17 条 Run、27 条 Turn、14 条 Task、17 条输入和 16 条操作。以下是 `OCTET_LENGTH(CAST(JSON AS CHAR CHARACTER SET utf8mb4))` 的字节数，不混用 KB/KiB。

| 位置 | 实测体积 | 说明 |
| --- | ---: | --- |
| 最大 `agent_runs.checkpoint` | 457,057 B（约 446 KiB） | 图片位于 `history.messages[4].parts[1].content[2]` |
| 其中 JPEG 的 `binary.data` | 406,604 B | base64url，约占该 checkpoint 的 89% |
| 对应图片段 `agent_turns.request_messages` | 895,677 B | 同一图片既有 406,604 B 的 SDK binary，又有 406,627 B 的 HTTP data URL |
| 对应图片段 `agent_turns.response` | 757,966 B | `normalized.history` 又有一份 406,604 B 的图片；原始响应另保留在 `raw` |
| 全表最大 Turn response | 785,570 B | 大 JSON 不只来自图片；不能用“没有图片”判断响应很小 |
| Task 的 context / skills / effective_state 最大值 | 1,254 / 3,027 / 5,478 B | 当前样本较小，后文列为结构性风险，不宣称它们已触发本次故障 |
| 输入 payload / 操作 result 最大值 | 3,265 / 11,453 B | 当前样本较小 |

同一图片在一个已完成段中至少有 **4 份持久化副本**，仅图片编码合计约 1.55 MiB；这不代表向供应商发送了 4 张图片或发生了 4 次模型计费。

### SQL 方案实测

从故障 Run 所属会话取得最近任务，本次为 2 个任务、4 条 Run。在相同 256 KiB 排序缓冲下进行 `EXPLAIN FORMAT=JSON` 和候选只读查询：

| 形态 | 结果 |
| --- | --- |
| 当前整行查询，`task_id IN (...) ORDER BY id` | EXPLAIN 使用 `idx_agent_runs_task`，仍有 filesort；原接口的 1038 由用户现场排查提供，本轮不重复执行整行失败查询 |
| 公共字段 + checkpoint/config 的 JSON 子字段，仍 `ORDER BY id` | 实际查询仍报 **1038** |
| 相同公共投影，`ORDER BY task_id, id` | 当前计划无 filesort，成功返回 4 条、序列化约 4,024 B |
| 相同公共投影，**无 SQL ORDER BY** | 成功返回 4 条、序列化约 4,024 B |
| 仅 id/task_id/conversation_id/status/phase，`ORDER BY id` | 成功返回 4 条、约 550 B，但字段不足以维持现有响应契约 |

关键修正：**不能把“用了 JSON_EXTRACT”视为已经把大 JSON 隔离出本次排序路径。** 必须用实际投影和查询计划验证。`used_columns` 中出现 checkpoint 也不等于响应返回了完整 checkpoint；是否失败以上述实际查询为准。

本地证据保存在被忽略的 `.runtime/assistant-context-audit.json`，不作为共享文档必须存在的依赖。输出仅含体积、结构路径和执行计划，未输出图片编码、密钥或用户提示词。

## 审查发现与修复方向

### 1. 🔴 阻塞：状态查询把大 checkpoint 带入排序路径

**位置**：[AssistantTaskService.task_runtime_state](../../../backend/src/short_drama/service/assistant_task_service.py)，约第 785–867 行；[read_run](../../../backend/src/short_drama/service/agent_run_service.py)，约第 60–113 行。

`select(AgentRun)` 先取整行，之后 `read_run` 才裁剪成 DTO。前端没有收到图片，不代表数据库没有处理图片。`read_run` 还读取 checkpoint 中的 `authorization.mode`、`awaiting_artifacts`，以及 config_snapshot 中的模型名，因此直接 `defer(checkpoint)` 会被随后的属性访问补查回来。

**最小修复**：

- 在 DAO 提供独立的状态投影，只取现有 RunRead 必需的字段及少量 JSON 子字段；不返回完整 checkpoint/config_snapshot，不产生可隐式懒加载的半实体。
- 当前 state 对 Run 没有 SQL 分页，优先让这条窄投影查询不带 `ORDER BY`，物化后按整数 id 在服务层恢复升序。排序对象只有公共元数据，不能先取完整大行再转到 Python 排序。
- 保留现有 Run 顺序、model_name、mode、awaiting_artifact_ids、预算、错误、排队位置、review 和恢复游标语义。前端使用 `runs.at(-1)`，不能直接把任务分组顺序作为新响应顺序。
- 将来需要 Run 分页时，先用仅含 ID 的有界查询完成排序/分页，再无排序批量读取投影，按第一步的 ID 顺序组装。不能简单加 LIMIT 丢掉活动或排队运行。

**验收**：原有大 checkpoint 不修改、缓冲不调大，故障会话 state 即可成功；运行模型、队列、停止/续聊、SSE 恢复游标和跨用户隔离均保持。数据库测试要使用 MySQL 和大 JSON，SQLite/纯替身不能覆盖 1038。

### 2. 🟡 应当修复 / P1：媒体展开结果穿过了全部持久化边界

**位置**：[media.py](../../../backend/src/short_drama/agent/context/media.py) 的 `_binary/materialize_prompt`；[runtime.py](../../../backend/src/short_drama/agent/coordinator/runtime.py) 第 557、668、746、1068 行附近；[protocol.py](../../../backend/src/short_drama/agent/gateway/protocol.py) 的 `serialize_history/run_segment`。

原素材已经在 MinIO，任务输入最初也保存定位值；但 `_decision` 展开后把 `claim.inputs.kwargs.user_prompt` 改回含 binary 的内容，`before_send` 又保存完整 HTTP 请求。网关序列化 `result.all_messages()`，完整历史随后进入 Turn response 和 Run checkpoint。下一段继续携带这些历史。音频和视频采样帧走同一条路径，潜在体积更大。

**方向**：应用层持久化使用版本化的媒体引用格式；SDK BinaryContent 和 HTTP data URL 只存在于本次发送或本地回放的内存中。四个落库入口必须一起处理，不能只在 checkpoint 上做递归删字段。

引用至少记录来源身份、冻结版本/校验值、MIME、处理后对象的稳定定位与 SHA-256；视频额外记录实际帧时间和音轨模式。**只存原始 media_id 不够**：当前图片经过缩放重编码，音视频经过采样/转码，日后重新执行处理不保证得到原请求的相同字节。

原始响应的 `raw.body_b64` 是响应回放证据，不是本次 JPEG 输入副本。不能把所有 base64、所有 `data` 字段或工具返回的同名 JSON 都判成媒体并删除。对大原始响应可另行评估外置存储，当前先隔离它与状态读取。

### 3. 🟡 应当修复 / P1：动态状态整块重发，压缩没有清理实际协议历史

**位置**：[prepare_decision](../../../backend/src/short_drama/agent/coordinator/assistant.py) 的 `state/active_skills`；[build_segment_prompt](../../../backend/src/short_drama/agent/context/prompt.py)；[compacted_history](../../../backend/src/short_drama/agent/task/compaction.py)，第 28 行附近。

现有 digest 能避免状态完全不变时重发，这是应保留的改进。但回执、输入或方法状态变化时，会重新发送整块 `inputs + active_skills + memory + receipts`，而旧状态块仍在 SDK history 中。`active_skills` 含完整 instructions 和已读 resource 片段；`load_skill` 和资料工具还各自返回正文，造成重复表达。

`compacted_history` 只替换内容恰好等于原 goal 的字符串；当前首段实际是“JSON 状态块 + goal”，不会命中。小型纯函数复核确认：该结构化首段经过压缩函数后完全不变；回执变化后，下一段再次含完整 Skill instructions 和所有 inputs。已有用户输入摘要不能等同于协议历史已瘦身。

**方向**：为应用生成的状态块提供可识别的类型和版本，在工具边界更新当前状态，不把每次完整状态都追加成永久的用户正文。活动 Skill 的目录与原文分开；原文在激活时保留一份，资源正文按需读取。协议历史整理需要实际回收旧状态块和可重读正文，同时保持最新用户要求、冻结方法约束及工具调用/返回的配对关系。不能任意切片 Pydantic AI messages，也不能用摘要替代授权和版本水位。

### 4. 🟡 应当修复 / P2：Skill 已经支持按需加载，加载后的重复保留仍可减少

**位置**：[freeze_skills](../../../backend/src/short_drama/service/agent_skill_service.py)，第 259 行附近；[skill/runtime.py](../../../backend/src/short_drama/agent/skill/runtime.py) 的 `_activate/skill_context/finish_resource_locked`。

已有三层读取：列表返回摘要、`load_skill` 读取冻结正文、`read_skill_resource` 按路径和 offset/limit 读取资料；列表还排除了 instructions 大列。**无需另建 Skill 搜索或加载系统。**

可减少的是：完整 Skill 被复制到输入 payload、task.selected_skills、effective_state 的 activation；资料片段又保存在 activation.resource_reads，并进入工具回执和模型历史。上限为 8 个活动方法、正文 128 KiB、资料片段 32 KiB，属于有界重复，不是当前数据库已爆大的证据。

**方向**：复用不可变 `AgentSkillVersion` 的 version_id、content_version、package_checksum；激活记录主要保留版本引用和读取区间。手动指定的方法在首段生效，不必再让用户确认一次；自动方法继续 search/load。正文仍遵守冻结版本和手动优先，不能静默换成最新版。先消除动态状态里的重复正文，再评估是否值得减少 task 中的存储副本。

### 5. 🟡 应当修复 / P2：核对单个画布节点会读取并锁定整张画布节点

**位置**：[assistant_subject_service.py](../../../backend/src/short_drama/service/assistant_subject_service.py) 的 `_current`，第 73 行附近；[AssistantContextDAO.canvas_nodes](../../../backend/src/short_drama/dao/assistant_context_dao.py)；[CanvasDAO.children](../../../backend/src/short_drama/dao/canvas_dao.py)。

`_current` 为一个 node 调用 `dao.canvas_nodes(canvas.id)` 后才在 Python 找 node_key；该 DAO 读取全部活动节点并 `FOR UPDATE`，包含 content_json。选入多个节点时会重复执行；`selection_metadata` 又被准备模型输入和发送前校验调用。结果虽然只投影一个主体，底层读取和锁定范围却更大。

**方向**：复用已有 `(canvas_id, node_key)` 唯一索引按节点读取；多节点按画布分组批量查询，并一次读取本人的私人版本。保留内容校验、归属、归档过滤和写入版本保护，不因优化绕过冻结检查。元数据核验与读取正文的职责应区分。

前端 `@` 候选只传节点身份和名称，选中项传身份/版本；画布保存屏障取得整张图是保存流程，不等于把全图发送给模型。不要因此修改画布自动保存或扩大助手到未选节点。标准素材/分镜和节点正文目前已有 `read_selected_subjects` 分段读取，应继续复用。

### 6. 🟡 应当修复 / P2：同类状态路径仍多取大列，并有逐项补查

**位置**：[task_runtime_state](../../../backend/src/short_drama/service/assistant_task_service.py) 的 Task、Operation、Input 查询；[read_task/read_operations](../../../backend/src/short_drama/agent/task/state.py)；[AgentRunService](../../../backend/src/short_drama/service/agent_run_service.py) 的 `list_runs/runtime_state`。

- Operation 列表取了 arguments、result、changes，展示却主要用状态和 result_refs；内部差异合法可达较大体积。详情/撤销需要这些内容，状态列表不应随带。
- Input 查询取完整 payload，最终只输出消息身份、输入水位和应用水位。
- Task 列表取 context_snapshot、selected_skills、effective_state，再剔除正文生成目录；主体快照上限 1 MiB，文本资料上限 128 KiB，不能以当前样本小判断一直安全。
- 新 state 中每个 Run 的 `read_run` 会另查待审工具，queued Run 另算队列位置；每个 Task 的 `read_task` 另查活动操作。旧 `list_runs` 已有批量 review 查询，可复用其方向。
- 兼容 runtime 和历史 Run 列表也会读取完整 AgentRun，应共享只读投影；执行器按 ID 加锁并加载 checkpoint 是另一类需求，不应全局禁止。

**方向**：状态/列表用显式 DTO 投影，详情/恢复保留完整记录；依赖的 JSON 子字段仍要遵守第 1 项实测结论。先排除 Input payload 和 Operation 差异等确定不需要的字段，再复用目录/版本数据减少 Task 大字段读取。review、活动操作和队列位置按当前页面批量读取。每项需有查询次数和大字段读取断言，不为本次审查扩成全库 DAO 重写。

## 对原修复建议的校正

| 建议或判断 | 本次审查结论 |
| --- | --- |
| 新增 `(task_id, id)` 覆盖索引即可免排序 | 当前 ORM 和实际数据库**已经有** `idx_agent_runs_task(task_id,id)`。它不是完整状态查询的覆盖索引，多 task IN 也不保证全局 id 顺序；不能重复加索引或保证彻底消除 filesort。 |
| 只投影必要 JSON 子字段即可立即修复 | 本机保留 ORDER BY id 的 JSON 子字段投影仍报 1038；无 JSON 的极简投影成功但缺字段。建议无数据库排序的公共投影，或先 ID 分页再读详情。 |
| 服务层完全吞掉异常、运维无从诊断 | 当前 BaseService 已在映射前记录 service、读写、request_id、project_id、异常类型和整数驱动错误码；DatabaseUnavailable 当前为 503。现场曾出现 500，应核对部署版本和日志收集，不能据此重做异常体系。 |
| 让前端显示 MySQL 原始报错 | 不应暴露 SQL、绑定参数、图片或驱动原文。保留安全错误码及请求标识；助手局部文案可改为“暂时无法读取此会话，已有内容仍保留”，避免暗示整个服务停止。 |
| 图片改存 media_id 即解决每轮计费 | 只改变持久化不会改变模型请求。历史每次重新展开仍会发送图片；还需上下文驻留/按需读取策略。图像计费不能按 base64 字符直接换算为文本 token，缓存折扣以 provider usage/cached_tokens 为准。 |
| 大行超过 sort_buffer_size 就必然失败 | 是否失败还取决于查询计划与排序载荷；本次失败路径和候选查询已有实测，不能把 256 KiB 当作所有 JSON 行的合法体积上限。 |

## 按需加载的目标行为

这里区分“资料仍然可找回”“本段模型真的看到了正文/像素”和“不可变原件可审计”。目录本身不能被当作已读取内容。

| 信息 | 默认进入模型的信息 | 何时加载完整内容 | 持久化依据 |
| --- | --- | --- | --- |
| 本条消息主动附加的图片 | 名称、所属消息、稳定顺序；本条明确请求分析时仍直接提供像素 | 本次分析；后续确需像素时再次读取 | 原素材身份 + 已处理像素对象引用/校验值 |
| 旧图片/音视频 | 原消息顺序、名称、类型、来源键及有依据的已读结论 | 比较、细节确认、修改等需要原内容时；不要求用户重新上传 | 同一冻结对象；视频帧时间、音轨模式保持 |
| 文本附件 | 名称、大小、来源键 | 按范围读取；精确改写所需原文不能只给摘要 | 附件冻结校验值/原文本，不复制进每份状态块 |
| 标准素材/分镜、画布节点 | 身份、名称、可用性和版本目录 | 复用 read_selected_subjects 的分段冻结正文读取 | 已冻结主体快照；不能拿 ID 回查最新正文冒充旧版本 |
| 图片组和生成图片 | 已有目录和回执身份 | 复用 read_image_group/read_image_content | 原组/图位/媒体身份及版本 |
| 手动 Skill | 已选版本、必要规则；首段按原版本生效 | 原方法规则在工作上下文中保留一份，资料按需读取 | 不可变 AgentSkillVersion |
| 自动 Skill | 检索摘要和激活目录 | 复用 search_skills/load_skill/read_skill_resource | 激活版本 + 资源校验值和读取区间 |
| 工具回执 | 状态、结果引用、版本、错误和撤销事实 | 已有 receipt/result 工具读取必要内容 | 完整操作账本和差异保留，不能为省空间破坏撤销 |
| 记忆 | 已有目录、摘要、近期必要消息 | 复用 read_memory/read_conversation_history | 现有来源和权限校验；不另起检索系统 |

现有 `read_image_content` 主要覆盖主体图片和本任务产物，未完整覆盖上传附件。确有需要时增加一个受控 `read_attachment_content`：文本返回有界片段，媒体返回下一段投递回执，复用既有处理和校验；不为每种素材另建工具体系。

“第二张图再改一下”仍由稳定的原消息/素材顺序定位并自动读取。名称重名不能误认，来源删除/撤回后不能通过已外置副本绕过权限，新任务不能因看到旧消息目录而自动获得读取权限。不会为每张图自动增加一次独立模型摘要调用；按需读取可能增加一个决策往返，需要在真实对话中比较质量、延迟与费用后启用。

## 分阶段实施

### 第一阶段：恢复会话状态读取

修改范围以 `dao/agent_task_dao.py`、`service/assistant_task_service.py`、`service/agent_run_service.py` 的查询与只读投影，以及现有助手 MySQL 测试为主。保持 HTTP DTO 不变；先完成故障 state，兼容状态路径复用同一投影，不改 Worker checkpoint 读写。

不调全局 sort_buffer_size，不迁移旧图片，不新增索引。验收用原始 446 KiB checkpoint 和 256 KiB 缓冲，确认 state 可读、顺序和恢复行为一致。Input/Operation 的确定多余字段可随投影一起排除；Task 完整目录的去重和所有批量补查不作为止血前提。

### 第二阶段：媒体不再重复落入数据库协议快照

修改范围涉及 `agent/context/media.py`、`agent/coordinator/runtime.py`、`agent/gateway/protocol.py` 的应用层编解码边界与现有媒体/回放测试；存储复用现有 MinIO 和受控对象能力。

1. 冻结处理后媒体对象。存好实际发送的 JPEG、音轨、采样帧并记录校验值；失败须发生在发送模型请求之前，不在数据库锁内执行下载/转码。
2. 持久化格式采用显式 codec/version，保留来源及协议顺序；在 SDK 边界才解析为原有 Pydantic AI messages/BinaryContent。网关不引入数据库或 Service 依赖，不开放任意 URL 下载。
3. 同步覆盖 checkpoint.history、Turn 冻结输入、Turn HTTP 请求、Turn normalized.history。序列化只处理类型明确的用户媒体槽，工具 JSON 原样保留。
4. 保留请求冻结、发送前准入、原始响应先持久化、受理不明及幂等保护。不能删掉请求正文或只留一个 hash 后失去回放依据；记录可重建的请求结构、媒体引用及校验摘要。
5. 恢复先取得已冻结的处理后对象，组成回放所需的本地输入包；`replay_segment` 仍只使用该包和原始响应进行本地校验，不临时访问 MinIO/DNS/供应商。取得本地包的存储读取不宣称为“离线”。对象不可读时明确暂停，不能自动重新付费请求。
6. 新旧格式可读、新写仅新格式。旧数据按终态小批次、校验值和版本条件转换，先 dry-run/备份；活动运行走兼容读取，不能与 Worker 抢写。旧数据不删除、不重跑工具、不修改原素材。查询止血不依赖先完成回填。

本阶段先保持历史图片的模型可见语义，验收持久化体积与图片大小脱钩；**不宣称本阶段已减少供应商输入用量**。

### 第三阶段：减少重复上下文，保留旧素材可继续使用

先做两项有明确代码证据的小改动：Skill/资料正文不再随每次动态状态重复注入；节点核验改为按指定节点批量查询。之后再实施旧媒体目录 + 按需读取和协议历史整理。

为应用状态块和已读内容建立来源范围标记，复用冻结的 Skill 版本、主体快照、附件和操作记录。保留一份当前必要上下文与完整审计记录，整理历史只在完整工具边界进行。当前/最近确需的图片可以驻留，较旧内容仍可由工具读取；不直接套用固定“最近 N 张”删图规则，也不静默截断方法或用户要求。

分别记录 SQL/响应字节、持久化字节、实际请求字节、模型输入/缓存用量，验证这四类收益。已有 segment/provider token 预算继续作为模型保护；持久化体积单独计量，不能把媒体估算占位当成已经缩小数据库。任何硬上限都应在外发前验证或可靠外置完整记录，不能在已付费响应回写时丢弃证据。

跨层实现时同步 [助手 API](../../api/assistant.md)、[系统架构与数据流](../../instruction/系统架构与数据流.md) 和 README；若最终新增表/字段，再补 ORM、迁移及 schema 导出，不提前建立占位表。
