# Agent 记忆系统存储与分层决策

状态：历史选型记录，已被修订版替代，尚未实施。日期：2026-10-21。

> 当前方案以 [Agent 无 Embedding 记忆系统设计（修订版）](2026-10-21-Agent记忆系统设计修订版.md) 为准。本轮确认继续使用 MySQL、不使用 embedding；会话仍全局独立，用户偏好跨会话、创作设定默认会话隔离、作品记忆显式绑定。以下原始评审中的 project-scoped 统一作用域、自动转向向量检索条件及未经当前源码验证的数量和产品类比，仅保留为历史背景，不作为实施结论。

本文记录五层记忆设计的评审结论与存储归属裁定。实施前需按第 5 节顺序推进，未实施部分不得按已完成对外描述。

## 1. 结论

| 议题 | 结论 |
| --- | --- |
| 存储方案 | 全部五层留在 **MySQL**，不引入 PostgreSQL |
| 召回方式 | **索引常驻 + 正文按需读取**，不引入 embedding / 向量检索 |
| 五层分层 | 保留，补四项机制 |
| L5 作用域 | 由 conversation-scoped 改为 **project-scoped** |
| 实施顺序 | L3 → L4 摘要 → L5 索引式记忆 |

不采用「助手数据整体独立」方案，也不采用 pgvector 方案。pgvector 仅作为规模突破后的备选，触发条件见第 7 节。

## 2. 不采用整体独立方案的原因

源码与 schema 核查结果：

1. `agent/tools.py` 的 `execute_tools` 注释明确「每个效果与其持久化结果共享同一个短事务与作用域锁」。同一事务内既 `lock_run()` 锁 `agent_runs`，又写 `ProjectScript` / `ShotScript` / `Asset` / `ProjectNovel`。会话与运行状态迁出 MySQL 后，该事务必然跨库。
2. `tools.py` 使用 `with session.begin_nested()`（SAVEPOINT）在工具校验失败时只回滚副作用、保留安全错误。跨库后 SAVEPOINT 语义不存在。
3. 9 张 `agent_*` 表中有 4 个外键指向业务表或自身：`agent_runs.initiated_by → users`、`model_config_id → ai_model_configs`、`trigger_message_id → agent_messages`。迁移后外键失效，需应用层补偿。
4. `agent_runs.active_conversation_id` 是 MySQL `GENERATED ALWAYS ... STORED` 生成列，配合唯一约束保证单会话单活跃运行。这是并发正确性的依赖，跨方言重写需逐字对齐。
5. 全库共 101 张表。为 9 张表引入第二套 DDL、备份、监控与迁移体系，收益与成本不匹配。

结论：整体独立方案迁走的是元数据，真正的耦合点（工具写业务表、外键指向业务表）仍留在 MySQL，形成「名义独立、处处跨库」的中间态。

## 3. 存储归属

| 层 | 内容 | 归属 | 说明 |
| --- | --- | --- | --- |
| L1 原始记录 | 完整对话、引用、工具结果 | MySQL `agent_messages` | 现有表，事务内追加 |
| L2 近期上下文 | 最近完整消息 | MySQL 查询 | 不落新表 |
| L3 任务状态 | 目标、约束、已确认决策、待办 | MySQL | 复用 `fixed_requirements` 与 run checkpoint |
| L4 会话摘要 | 分段摘要与阶段总结 | MySQL 新表 | 文本型，无向量需求 |
| L5 长期记忆 | 用户偏好、作品设定 | MySQL 新表 | 索引常驻，正文按需读，无向量 |

五层全部使用 MySQL。PostgreSQL 与 embedding 均不引入，L5 的召回改为第 4 节的索引式方案。

## 4. 召回方式：索引常驻 + 正文按需

### 4.1 参考依据

Codex 与 Claude Code 均不使用向量检索，二者记忆系统的实际做法：

- **Claude Code**：`MEMORY.md` 作为索引，每次会话只加载前 200 行或 25 KB；主题文件（`user_role.md`、`feedback_testing.md` 等）启动时不加载，由模型按需用文件工具读取。记忆分四类 `user` / `feedback` / `project` / `reference`，并主动跳过可从代码库推断的内容。超限不截断，而是报错要求重写索引。压缩后根 `CLAUDE.md` 从磁盘重新读取并重新注入。
- **Codex**：项目根 `AGENTS.md` 启动加载，`project_doc_max_bytes` 默认 32 KiB 截断，嵌套目录就近覆盖；配合 `/compact` 压缩与 `codex resume` 恢复会话。会话以 JSONL 落盘。
- **PRO-LONG 实测**（arXiv:2607.20064）：约 30 行提示 + 结构化决策日志 + grep 检索，优于 600 行提示 + 多 MCP 工具 + 4 个专用 agent，提升约 18 个百分点。

共同模式：常驻内容永远是小索引且有硬上限，正文按需取，超限强制重写而非静默截断，压缩后索引重新注入。

### 4.2 本项目方案

L5 记忆表（MySQL，无向量列）：

```
agent_memory_items
  id, owner_user_id, project_id, kind, title, content,
  source_message_id, supersedes_id, forgotten_hash,
  hit_count, last_used_at, modified_at, status
```

`kind` 采用 `user` / `feedback` / `project` / `reference` 四分类，使抽取有明确取舍标准，避免"觉得有用就记"。

召回分两段：

1. **索引常驻**：每轮把 `kind + title` 一行一条注入提示词，上限 150 行（约 1200 token），位置在 `fixed_requirements` 之后的稳定区。
2. **正文按需**：模型根据索引调用 `read_memory(id)` 读取全文，走现有 `tools.py` 的 `_execute` 分支，不新增协议。

模型不再被动接收 top-k，而是知道存在哪些记忆并自行决定读取对象。

### 4.3 配套规则

- **抽取过滤**：角色名、分镜数、剧本结构等可从 `project_novels` / `shot_scripts` / `assets` 直接查询的内容不写入记忆。只记用户偏好、明确纠正、以及数据里推不出的决策。
- **写入低频**：记忆不在每轮写入，由 Celery 在对话结束后批处理。索引频繁变动会使提示词缓存整体失效。
- **索引硬上限**：超过 150 行时按 `last_used_at` 最旧、`hit_count` 最低淘汰并合并，不静默截断。
- **删除可见**：记忆需在界面列出并支持删除，删除写 `forgotten_hash` 墓碑，抽取时跳过。

### 4.4 成本依据

向量方案每轮需一次 embedding 调用与一次相似度查询，属实时开销且不参与提示词缓存；索引方案常驻部分为稳定内容，可命中提示词缓存，正文只在模型实际读取时产生 token。本项目为单创作者、单项目场景，索引方案在成本与实现复杂度上均占优。

## 5. 五层设计需补的四项机制

### 5.1 单一压缩水位线

L2 与 L4 的边界必须由唯一水位线仲裁，不允许两条独立规则各自判断。

- `agent_conversations` 增加 `summary_covers_until_seq`
- L2 起点固定为 `summary_covers_until_seq + 1`
- 任何摘要写入必须先读该字段并在同一事务内推进，避免重叠或漏读

不加水位线的后果：某条消息既不在原文窗口、也不在任何摘要中，用户明确提出的要求凭空消失且无法复现。

### 5.2 摘要版本与消息序绑定

摘要记录必须携带 `from_seq`、`to_seq`、`version`、`status`，复用现有 `next_message_seq`。

- `status` 至少包含 `pending` / `ready` / `stale`
- 后台预计算期间到达新消息时，摘要转为 `stale`，不得继续启用
- 已启用摘要被判定过期时，退回原文窗口而非沉默使用旧摘要

### 5.3 冲突消解与遗忘墓碑

长期记忆需要两条同等重要的机制：

- **冲突消解**：`supersedes_id` 与 `valid_from` / `valid_to`。同一偏好在不同时间被改写时新增记录并标记旧记录失效，不原地覆盖。
- **遗忘墓碑**：用户删除记忆后写入 `forgotten_hash`。抽取任务先查墓碑，命中则跳过。缺少此表时，原始记录仍在，同一条记忆会在下次抽取时被重新生成。

### 5.4 任务状态双来源

L3 不得由模型单方面写入。必须区分：

- `fixed_requirements`：用户显式确认的约束
- plan / checkpoint：模型提议、尚未确认的内容

两者在提示词中分别标注来源。混为单一 blob 会导致模型把猜测当成已确认决策，并被后续每轮当作事实继承。

## 6. 实施顺序

1. **L3 任务状态**：明确双来源，补齐来源标注。纯 MySQL，无新组件。
2. **L4 会话摘要**：新增摘要表、水位线字段、后台预计算任务与 `stale` 判定。纯 MySQL。
3. **L5 索引式记忆**：新建 `agent_memory_items`，实现索引注入、`read_memory(id)` 工具、抽取过滤、淘汰合并与遗忘墓碑闭环。
4. **验证**：观察索引命中率、记忆读取次数与用户纠正频率。第 3 步的召回质量是本方案成立的前提。

第 3 步完成前不引入任何向量组件。若第 3 步显示瓶颈在提示词装配或上下文截断，而非召回精度，则不应转入向量方案。

## 7. 何时才引入 embedding

仅在下列任一条件成立时才评估 pgvector，届时只需新增一张向量表，`agent_memory_items` 仍留在 MySQL：

1. 单项目记忆条数超过 500，索引无法纳入上下文预算。
2. 用户表述与记忆用词系统性不匹配，标题与关键词匹配失效（例如用户说"那个反派"，记忆记为"陈墨"）。
3. 出现跨项目检索需求，例如"我以前写过类似的开场吗"。

embedding 若引入，模型倾向 `bge-m3`（1024 维，支持长文本）。`ai/gateway.py` 目前无 embedding 通道，需新增独立接口，不复用对话 composer。

## 8. 边界与未决事项

- 本文不含表结构 DDL。实施时按项目约定同步 ORM、真实库 DDL、`schema.mysql8.sql`。
- 多租户隔离：`owner_user_id` 必须在 DAO 层强制注入，不得作为可选查询条件。
- 大结果存储：工具返回的图片/视频正文只存引用，明细走 `agent_artifacts` 与 MinIO，正文截断存储。
- 压缩对用户可见：界面需在压缩边界标注，避免用户以为模型仍看到原文。
- 索引注入位置影响提示词缓存命中率，实施时需与 `runtime.py` 的提示词装配顺序一并确认。
