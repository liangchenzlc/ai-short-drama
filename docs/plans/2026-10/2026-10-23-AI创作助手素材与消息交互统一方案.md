# AI 创作助手 · 素材与消息交互统一方案

**日期：** 2026-10-23
**状态：** 进行中（P0–P2 已实施）
**范围：** 标准工作台 AI 创作助手（`frontend/src/features/ai-assistant`、`frontend/src/features/agents`，必要时配合 `backend/src/short_drama/{service,agent}`）

---

## 1. 背景：为什么现在的交互让人困惑

用户在输入区里添加的任何东西——本地文件、资产库图片、素材卡片、分镜卡片——在用户看来都是**同一件事：给这条消息加一张素材**。但实现里是两套状态、两种生命周期、两套视觉：

| 用户动作 | 落到哪里 | 生命周期 | 界面位置 |
| --- | --- | --- | --- |
| `+` 上传图片/文本、资产库选择 | `AgentAttachment`（`attachment_ids`） | 随消息发送即清空 | 输入框上方药丸行 |
| `@` 选素材卡片/分镜卡片、点「选入当前主体」 | `subject_selection`（任务引用草稿） | **任务级累积，永不自动清空** | 另一排 chips（含 `· v2` 版本号） |

于是出现截图里的现象：消息已经发出去了，输入区下方仍然挂着「选入当前主体」按钮和「永明钟表店 · v2 ×」标签。用户要的是**和上传附件完全一样的待遇**：添加 → 出现在输入框顶部 → 发送 → 从输入框消失 → 以缩略图/标签的形式挂在那条消息上。

同类产品（ChatGPT、Claude、豆包、Gemini 等）的通行做法一致：

1. 附件/素材一律显示在输入框上方，来源不可见、不做分类；
2. 发送后输入框清零，素材以缩略图或文件标签挂在**那条消息**上；
3. 对话里如果要特别说明某张图，用 `@文件名` 在正文里指名（只是引用，不改变素材集合）；
4. 之后继续聊这张图时，模型仍然认得（它在对话历史里），用户不需要重新添加。

本方案按这个范式统一 AI 创作助手，并把此前排查出的 5 处非常规交互一并修掉。

## 2. 目标交互（用户旅程）

### 2.1 添加素材
- 输入框底部的 `+` 提供全部入口：本地图片/文本、资产库素材、（画布模式下）当前画布。
- `@` 列表的「可能 @ 的内容」= **当前这条消息已添加的全部素材**，不区分来源；下面是作品里的素材卡片/分镜卡片。
- 添加成功后，素材以 **30px 药丸**出现在输入框正上方：`[22px 缩略图] 文件名（省略） ×`。
- 同一条消息可添加多项，超限提示「一条消息最多 16 项素材」。

### 2.2 在正文里引用
- 输入 `@` 弹出候选：当前消息素材排最前（缩略图 + 名称），其次作品素材/分镜。
- 选中后正文写入 `@名称` 并**行内高亮**（与 `/方法名` 同一套高亮层）；Backspace/Delete 一次删掉整个词条。
- `@名称` 只是「指名这张素材」，**不新增、不移除**素材集合。模型收到的提示里本来就带 `附件 {名称}：` / `资料 {名称}：` 前缀，指名可被准确对应。

### 2.3 发送
- 发送成功后，**输入框上方的素材条整体清空**，正文清空，输入区回到初始状态。
- 素材随消息冻结：此后再改素材库里的原图，不影响已发送消息里的这张图。

### 2.4 消息上的素材
- 发送出去的消息气泡下方显示这条消息的素材：
  - 图片 → **56×56 缩略图**，点击可放大；
  - 文本 → **3 行摘要小卡**（文件名放 title）；
  - 音视频 → 40px 图标卡（不展开播放器）。
- 不显示「附件 1、附件 2」式的文件名列表，不显示校验和、大小、ID。
- 助手回复里产生的产物（生成图、候选）沿用现有产物卡，不与素材混排。

### 2.5 下一条消息
- 新消息的素材条初始为空；要继续用旧图，`@` 历史消息里的素材名，或重新添加。
- **模型侧**（见 §6 决策点）：历史消息里的素材仍在对话上下文里，用户说「第二张图改一下」时模型认得，不需要重新上传。

## 3. 统一后的数据模型

用户可见层只有一种「素材」，实现层保留两条数据路径（各自有独立校验），但**生命周期与展示完全一致**：

```
消息素材 = attachment_ids（文件：本地上传 / 资产库引用 / 画布引用）
         + subject_selection.subjects（结构化：素材卡片 / 分镜卡片）
```

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 发送时 | `attachment_selection` 可选；`subject_selection` 可选，省略=沿用任务旧集合 | 任务级草稿（`attachmentDraft`/`subjectDraft`）**取消**；引用随消息提交（`retain_keys` 保留任务已有快照 + `subjects` 并入本条新增），附件沿用任务累积 —— 见 §6 选 B |
| 发送后 | 任务集合继续显示在输入区 | 输入区清空 |
| 版本号 | chips 显示 `· v{revision}` | 只在「素材在发送前被改动」时提示「有新版本」 |
| 「选入当前主体」 | 独立按钮 | 移除；当前页主体本来就出现在 `@` 列表里 |
| 消息展示 | 引用列表（名称/播放器/详情） | 统一缩略图标签 |

**接口侧**（`docs/api/assistant.md` 已支持，无需新字段）：
- `subject_selection.retain_keys` = 任务已有快照 key + `subjects` = 本条消息新增素材（只在有新素材时提交）；
- 附件走 `attachment_ids`，不提交 `attachment_selection`，任务内历史素材保持可见；
- `expected_input_revision` 用发送前现读的水位（`GET /tasks/{id}/subjects`），不再有「请核对附件/引用」流程。

## 4. 分阶段实施

### P0 消除输入区残留与两套状态（必做，先解决当前投诉）

**做什么**

1. **主体引用按消息隔离**（与附件同构）：
   - 删除 `subjectDraft` 的持久化（`assistant-draft.ts`）与「采用当前任务引用」机制（`AssistantSubjects` 的 stale 警告、`prepare()` 的抛错）。
   - 发送时由新的 `assistant-subject-scope.ts` 读取水位，统一提交 `subject_selection.retain_keys=[]` + 本条消息的 subjects。
   - 发送成功后 `setSubjectDraft(null)` 并清空素材条（现状已清 added，但 retained 仍来自任务）。
2. **移除「选入当前主体」按钮**（`AssistantConversationBody.contextChips`）；当前页主体保留在 `@` 列表。
3. **合并素材条**：`AgentContextComposer` 的附件药丸行 + `AssistantSubjects` 的引用 chips 合并为一条，样式统一为 §2.1 的药丸；引用卡片/分镜卡片显示其图片缩略图（无图用类型图标）。

**涉及**：`AssistantConversationBody.tsx`、`AssistantSubjects.tsx`、`AgentContextComposer.tsx`、`assistant-draft.ts`、`assistant-subject-scope.ts`（新）、`assistant-attachment-scope.ts`。

**验收**：发送任意消息（含 @ 素材卡片）后，输入区无任何残留；连续发两条不出现「任务引用已变化 / 任务附件已变化」；`@` 能选到刚添加的素材。

### P1 消息上的素材标签

**做什么**：`AssistantMessage` 把 `references` 里的 `type=attachment` 与引用素材统一渲染为 §2.4 的缩略图；`type=context/skill` 等非素材引用保持现状。素材名称只作 tooltip。

**涉及**：`AssistantMessage.tsx`、`ai-assistant.css`。

**验收**：带图发送后，消息下方是 56×56 缩略图；文本是 3 行摘要；不再出现文件名列表与播放器。

### P2 五处非常规交互（见 §5）

### P3 收尾与文档
- 更新 `docs/api/assistant.md` 的前端行为描述（「引用通过 @、当前主体…」段落）。

## 5. 五处非常规交互的修复方案

| # | 问题 | 现状 | 改法 | 阶段 |
| --- | --- | --- | --- | --- |
| 1 | **引用草稿陷阱** | `subjectDraft` 持久化后任务一变就卡死发送（「任务引用已变化，请先核对引用草稿」） | 随 P0 删除草稿与 stale 机制，引用随消息提交 | P0 |
| 2 | **内部版本号/ID 外露** | 引用标签「永明钟表店 · v2」；讨论历史「版本 3 · 来源消息 9007… · 回复运行 9007…」 | 标签只显示名称；仅当「发送前素材被改动」时提示「有新版本，点此采用」；历史行改为「编辑前 / 重答前 + 时间」 | P2 |
| 3 | **聊天报错混进「保存状态」** | 助手的错误/警告进入全局 `StudioFeedback` store，出现在文档保存状态面板 | 给反馈增加作用域（`chat` / `document`），`StandardSaveStatus` 只显示 document 作用域；助手问题只在助手内联显示 | P2 |
| 4 | **两个加载入口** | 「载入更早消息」「载入更早任务」并存 | 合并为一个「载入更早」，内部同时补齐更早任务与消息 | P2 |
| 5 | **素材展示不统一** | 附件药丸行 + 引用 chips 两排、两种样式 | P0 合并为一条素材行 | P0 |

补充（P2 顺手做）：
- 发送受阻原因已在输入区上方内联显示，保留；`blocked` 的每个条件都要有对应可见提示，不允许「按钮灰着但没说为什么」。
- 「作品上下文已截取」改为「内容较长，已截取」。

## 6. 决策点：模型是否继续看到历史素材

| 方案 | 说明 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 严格按消息 | 每条消息只带自己的素材，旧图下一轮即从模型上下文移除 | 与「附件按消息隔离」字面一致，省 token | 用户说「第二张图改一下」时模型看不到图，需重新 @；与市面产品体验不一致 |
| **B 展示按消息、对话可见（已选定）** | UI 上素材只挂在所属消息、发送后清空；模型上下文里保留历史消息的素材 | 与 ChatGPT 等一致：聊过的图可以继续聊 | 历史素材会重复注入提示；任务素材合计上限 16 项 |

**已选 B**：同时满足「发送后输入框清空」和「后续消息仍能讨论旧图」（“第二张图改一下”这类指代可用）。代价是历史素材会逐轮回到提示里，任务素材合计上限 16 项；后续可用「最近 N 项回灌 + 其余仅给名称清单」做上限优化，本次不做，避免「刚才那张图」指代失效。

## 7. 风险与兼容

- **草稿迁移**：`attachmentDraft`/`subjectDraft` 不再被读取，旧本地草稿里的这两段直接忽略，正文与 Skill token 保留。
- **水位冲突**：`expected_input_revision` 不匹配时自动重取一次再发；仍失败才提示「任务刚收到新输入，请重试」，不做静默重放。
- **历史消息**：已发送消息的 `references` 已含 `type=attachment` 与 `media_id`，读取时会补 `url`，P1 可直接渲染，无需迁移数据。
- **画布模式**：`AgentConversationRuntime` 不使用 `ComposerAttachmentsContext`，保持默认空数组，行为不变。

## 9. 实施记录（2026-10-23，P0–P2）

**P0 消除残留与两套状态**

- `AssistantSubjects`、`AssistantAttachments`、`assistant-attachment-scope` 删除；`assistant-materials.ts` 接管消息素材（`mergeMaterials` 合并去重、上限 16，`inspectMaterials` 读取名称，`subjectSelectionFor` 组装引用集合）。
- 发送后输入区清空：素材（附件 + 素材卡片/分镜卡片）统一走输入框上方的药丸行（`AgentContextComposer` 新增 `materials` 属性），发送成功 `setMaterials([])`。
- 「选入当前主体」按钮与引用 chips 行整体移除；当前页主体由 `@` 列表提供，选中后进素材行。
- 任务级草稿（`subjectDraft`/`attachmentDraft`/`references`）不再持久化，「任务引用已变化 / 采用当前任务引用」整套机制删除。

**P1 消息上的素材**

- 消息气泡把 `type=attachment` 渲染为缩略图（图片 56×56、文本 3 行摘要、音视频图标），`type=subject` 渲染为名称标签（素材卡片暂无缩略图 URL，需后端在 `selection_references` 补 `media_id` 后再升级）。

**P2 五处非常规交互**

1. 引用草稿陷阱 → P0 已删除。
2. 内部编号外露 → 引用标签只剩名称；讨论修订记录改为「编辑前/重答前 · 时间」，不再显示 `版本 N / 来源消息 / run_id`；「核对当前消息 · 版本 N」去掉版本号。
3. 聊天报错混进保存状态 → `StudioFeedback` 新增 `scope="chat"`：助手提示以内联 Alert 呈现在对话里，不进入 `StudioFeedback` 全局 store，文档「保存状态」面板不再出现聊天问题，弹窗提示也不再带「查看详情」。
4. 两个加载入口 → 合并为一个「载入更早」（先补更早消息，消息补完再补更早任务）。
5. 素材展示不统一 → P0 已合并为一条素材行。
6. 补充：「作品上下文已截取」改为「内容较长，已截取」。

**决策**：§6 选 B（展示按消息、模型可见历史素材）。附件不提交 `attachment_selection`（任务内累积），引用提交 `retain_keys` 保留已有快照 + `subjects` 并入新增。

**验证**：`tests/assistant` 44 项通过；`--changed --runner node` 373 项通过；`tsc --noEmit`、`vite build`、`check-docs`、`check-quality` 通过。`test-map.json` 补登记 `assistant-materials.ts`，移除 `AssistantSubjects.tsx`。

**未验证**：真实模型下「第二张图改一下」的跨消息指代；素材卡片缩略图（待后端补 media）。

### 补充修复（同日）：发送被拒与「核对状态」提示

**现象**：带素材发送时报「填写内容不符合要求，请检查后重试。」，且界面多处出现「核对状态」按钮，用户不知道点它做什么。

**根因**

1. `subjectSelectionFor` 把任务里**已有**的素材 key 全部写进 `retain_keys`，同时又把同一批素材作为 `subjects` 提交，服务端 `freeze_selection` 判定同一主体被保留两次，抛 `invalid_selection` 422（「刷新主体时不能同时保留该主体的旧引用」）。
2. 前端 `http.ts` 对 422 一律回落到通用文案，**丢弃了服务端自带的中文说明**；`invalid_selection` 等业务码也没有映射。
3. 所有错误条共用一个「核对状态」按钮，实际动作是「重建连接/刷新状态」，名不副实。

**修复**

- `assistant-materials.ts` 新增 `retainedSubjectKeys`：本条消息重新提交的素材从 `retain_keys` 中剔除（等价于刷新），新增 3 条单测覆盖「重复保留即 422」这一回归。
- `materialReference` 只对画布节点回传 `content_revision`，校验和仅在 64 位 hex 时回传，避免被 schema 拒绝。
- `http.ts`：4xx 且非 `validation_error` 时优先展示服务端中文说明；补充 `invalid_selection`/`selection_required`/`assistant_selection_changed`/`assistant_context_blocked` 的友好文案。
- 提示与按钮重写：连接中断 →「重新连接」；操作反馈 →「知道了」（可关闭）；待确认 →「刷新状态 / 重发原消息」；失败兜底改为「请检查模型配置后重试」。全文移除「核对状态」「使用原请求核对」等内部术语。

**验证**：`tests/assistant` 47 项（新增素材单测 3 项）、`--changed --runner node` 全过；`tsc`、`vite build`、`check-docs`、`check-quality` 通过。
