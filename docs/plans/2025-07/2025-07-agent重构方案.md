### 迁移策略

- 外部 `service/` 和 `tasks/` 共有约 36 条 import，随重构一次性更新到新路径。

- 迁移时只移动文件 + 更新 import，不修改函数签名；Bug 修复和结构迁移合并到同一次提交。

## 二、各系统问题修复方案

### 2.1 记忆系统

#### 问题 1：全局偏好用正则识别，脆弱

**现状**  
`memory_context.py:335` 通过 `re.search(r"以后|始终|一贯|...")` 决定是否写入跨会话记忆。

**修复**  
将决策责任交给 LLM。在 extract 任务的 instructions prompt 中明确说明：
- 只有当用户的原始表达中清楚体现"所有对话/今后所有/一直如此"等全局意图时，才在返回 JSON 中将 `scope_type` 置为 `"user"`
- `"user"` 范围等同于写入永久跨会话偏好，请谨慎标注

删除 `settle_maintenance_locked` 中基于正则的 `global_preference` 覆盖逻辑，直接信任模型返回的 `scope_type`。

保留一条后置校验：若 `scope_type == "user"` 但来源消息不含任何"以后/始终/一贯/长期/所有/一直/每次/往后/下次/统一"之类指示词，降级为 `"conversation"` 并记录警告日志（而非直接拒绝，保留可审查性）。

---

#### 问题 2：extract 水线被失败任务永久卡死

**现状**  
`extraction_waterline()` 是顺序区间扫描，失败的 job 无重试逻辑，水线永久卡住。

**修复**  
在 `AgentMemoryJob` 上已有 `attempts` 字段。在 `schedule_maintenance_locked` 和 `fail()` 中：
1. 失败时若 `attempts < 3`，以指数退避（15s × attempts）重新入队（extract 比 model 便宜，可多试）。
2. `attempts >= 3` 时将 job 标记为 `abandoned`（新增终态，区别于 `failed`）。
3. `extraction_waterline()` 计算时将 `abandoned` 视同 `succeeded`，跳过失败区间继续向前推进。

```python
# memory/context.py 修改后
def extraction_waterline(session, conversation_id):
    ranges = session.execute(
        select(AgentMemoryJob.from_seq, AgentMemoryJob.to_seq)
        .where(
            AgentMemoryJob.conversation_id == conversation_id,
            AgentMemoryJob.kind == "extract",
            AgentMemoryJob.status.in_(("succeeded", "abandoned")),  # 新增 abandoned
        )
        ...
    ).all()
```

#### 问题 3：summary 等待时仅 3s 平退，无退避

**现状**  
`claim_execution()` 检测到 `agent_memory_waiting` 时，以固定 3 秒 `mark_scheduled`。

**修复**  
在 run checkpoint 中记录 `memory_wait_count`，按 `3 × 2^(count-1)` 秒退避，最大 60 秒：

```python
count = (run.checkpoint or {}).get("memory_wait_count", 0) + 1
delay = min(60, 3 * (2 ** (count - 1)))
mark_scheduled(run, phase="model", when=now + timedelta(seconds=delay))
checkpoint["memory_wait_count"] = count
```

成功执行后清零 `memory_wait_count`。

#### 问题 4：task_state 类型与通用 Memory Store 耦合

**现状**  
`AgentMemoryStore._admitted()` 和 `settle()` 中有 `if job.kind == "task_state"` 分支，lazy import `task_compaction`，产生隐式双向依赖。

**修复**  
定义 `MemoryJobPlugin` 协议：

```python
# memory/runtime.py
class MemoryJobPlugin(Protocol):
    def job_current(self, session, conversation, job) -> bool: ...
    def settle(self, session, conversation, job, payload, usage) -> bool: ...
```

`AgentMemoryStore` 接受可选 `plugins: dict[str, MemoryJobPlugin]`，`task_compaction.py` 在 Worker 启动时注册 `"task_state"` 插件。Memory Store 本身不再 import task_compaction。

### 2.2 工具系统

#### 问题 5：assistant_tools.py 的工具执行是 if/elif 链

**现状**  
`execute_tools()` 内部超过 1000 行的条件分支。

**修复**  
新增 `tools/registry.py`，定义工具注册表：

```python
# tools/registry.py
from dataclasses import dataclass
from typing import Callable, Any

@dataclass(frozen=True)
class ToolHandler:
    prepare: Callable   # 准备/校验（在 SQL 锁内）
    execute: Callable   # 执行（可能在锁外做 I/O，如 MinIO 读取）
    finish: Callable    # 结果回写（在锁内）

TOOL_HANDLERS: dict[str, ToolHandler] = {}

def register(name: str):
    def decorator(cls):
        TOOL_HANDLERS[name] = cls()
        return cls
    return decorator
```

各工具模块（`standard.py`, `media.py`, `image.py` 等）各自使用 `@register("tool_name")` 注册。

`execute_tools()` 的核心循环简化为：

```python
handler = TOOL_HANDLERS.get(operation.tool_name)
if handler is None:
    raise ValueError(f"unknown tool: {operation.tool_name}")
result = handler.execute(session, conversation, run, task, operation, settings)
```

**修复**  
在 `_read_context()` 的 project 返回中加入计数和截断标记：

asset_total = session.scalar(

### 2.3 Skill 管理系统

#### 问题 7：用户已手动选 Skill 时仍强制先搜索

**现状**  
`load_skill_locked()` 要求 skill_id 必须出现在最近的 `search_skills` 结果中。

**修复**  
新增跳过条件：若 skill_id 存在于任务的冻结手动选择（`task.context_snapshot["selected_skills"]`），直接跳过 discovery check：

```python
def load_skill_locked(..., values, ...):
    key = values.skill_id
    # 手动选择的方法允许直接加载，无需先检索
    manual_ids = {item["id"] for item in (task.context_snapshot or {}).get("selected_skills", [])}
    if key not in manual_ids:
        # 原有的 discovered 检查
        if not any(...):
            raise WorkflowError("assistant_skill_not_discovered", ...)
```

#### 问题 8：版本冻结后用户无感知

**修复**  
在 `skill_context()` 组装激活列表时，若本任务加载的版本低于该 skill 当前最新启用版本，在 activation summary 中加入 `"stale_version": true` 字段。

前端暂无渲染要求；后端在 LLM instructions 注入 skill context 时自动带上说明：
> 「此方法已有新版本，当前任务仍使用冻结的旧版本，如需新版请开启新任务」

检查是否有新版本用一次轻量查询（`SELECT MAX(content_version) WHERE skill_key=? AND enabled=1`），结果缓存在 `task.effective_state["skill_version_hints"]` 中，首次组装时填充，不重复查。

**修复**  
在 `apply_manual_skills()` 中，当用户重新选中某个 skill_id 时，同步从 `excluded_skill_ids` 移除：

state["excluded_skill_ids"] = sorted(

### 2.4 中断系统

#### 问题 10：无法真正中断模型 HTTP 请求（最重要）

**现状**  
`heartbeat()` 失败后只设 `delta.disabled = True`，底层 HTTP 请求继续运行直到模型响应完毕。

**修复**  
在 `coordinator/runtime.py` 的 `_decision()` 中，capture 当前 asyncio Task 引用，heartbeat 失败时取消该 Task：

```python
async def _decision(self, claim):
    decision_task = asyncio.current_task()   # 捕获当前 Task

    async def maintain():
        last_heartbeat = time.monotonic()
        while True:
            await asyncio.sleep(0.2)
            delta.flush()
            if time.monotonic() - last_heartbeat >= max(5, self.settings.agent_lease_seconds // 3):
                if not self.store.heartbeat(claim):
                    delta.disabled = True
                    decision_task.cancel("heartbeat_lost")  # 【新增】真正取消
                    return
                last_heartbeat = time.monotonic()

    maintenance = asyncio.create_task(maintain())
    try:
        result = await self.gateway.run_segment(...)
    except asyncio.CancelledError:
        raise LeaseLost()          # 翻译为已有错误类型
    finally:
        maintenance.cancel()
        with contextlib.suppress(asyncio.CancelledError):
            await maintenance
```

`asyncio.CancelledError` 会通过 `gateway.run_segment()` 内部的 `asyncio.timeout` 上下文管理器向上传播，触发 `httpx2.AsyncClient.__aexit__` → `bridge.aclose()` → `stop.set() + feed_task.cancel()`，真正关闭 HTTP 流式连接。

预期效果：用户点击停止后，模型端 HTTP 请求在下一个心跳周期（最多 5 秒）内被中断。

#### 问题 11：等待异步生成期间控制信号积压

**现状**  
`apply_controls_locked()` 只在 `claim_execution()` 时被调用，任务处于 `waiting_generation` 时控制信号无法被及时消费。

**修复**  
在 `media_runtime.py` 的 `collect_media_results()` 结果循环中，每轮收集前检查是否有 stop/delete 控制信号：

```python
# native/tasks.py 和 media/runtime.py 的收集入口
dao = AgentTaskDAO(session)
if dao.controls(task):
    # 有 stop/delete 信号，直接结束收集，让下一次 claim_execution 处理
    return {"status": "control_pending"}
```

调度器 `tasks/runtime.py` 检测到 `control_pending` 时，提前触发一次 agent worker，让 `apply_controls_locked` 被执行。

#### 问题 12：stop 后 redirect 被静默丢弃

**现状**  
`task_controls.py:28` 直接 `continue` 跳过，用户毫无感知。

**修复**  
记录被跳过的指令到任务事件流，不静默丢失：

```python
for control in controls:
    if stopped and control.kind == "redirect":
        task_event(
            session, conversation, task, "control.skipped",
            run=run, control_id=str(control.id), reason="task_already_stopped"
        )
        control.applied_at = now  # 标记已处理，不重复积压
        continue
```

前端可选择展示"任务已停止，你的修改请求未被应用，请在新任务中重新输入"。
