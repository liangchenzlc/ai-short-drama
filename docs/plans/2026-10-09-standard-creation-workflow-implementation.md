## 4. 契约补齐与数据落地

### C1. 空白卡片与有效素材的创建边界

点击新增立即生成界面草稿、追加并选中卡片，整个过程不出现创建弹窗。“全部”下 `kind` 未选择；角色、场景和道具分类沿用当前类型，名称、描述及提示词为空。

草稿拥有独立临时标识，不能把 UUID 发成业务数据库 ID。名称与类型完整后，复用现有 `assetLibraries.create` 和创建幂等键保存；成功回执原位替换临时标识，卡片不重复、选择不跳走，并更新助手引用。请求受理不明时保留原键核对，不能创建第二张素材。

空白草稿按账号、项目、分集保留在本机恢复记录中。离开页面有输入时沿用草稿保护；失败保留卡片和输入，就近显示重试。没有名称／类型时禁用生成；其他生成准入仍按原业务校验执行。“未命名素材”是占位文字，不能自动作为真实名称提交。

镜头已有允许空脚本的创建接口，优先复用现有 `add()` 流程和 `storyboard_version`，无须为了对齐视觉强行改成临时素材式事务。名称补齐前禁用生成；不改变脚本非空、模型与参考图片校验。

### C2. 已保存素材的类型修改

确认方案的类型选择需要真实保存。实施前公开 HTTP 使用的 `AssetPatch` 拒绝 `kind`，泛用 `AssetUpdate` 中有该字段并不代表当时公开接口允许变更。现已扩展 `AssetPatch` 与前端 DTO，实际保存与兼容验证见实施验收记录。

实施时同步扩展公开请求与前端 DTO，保留 `row_version`、权限和共享影响确认。服务端验证新类型与 `scene_time`、角色对白／声音、镜头关联等依赖是否兼容；不允许的转换返回明确错误并保留草稿，不能自动删关联或清空旧数据。允许的变更取消受影响的旧确认，按实际上下文标记需要核对的媒体。

现有 `assets.kind` 已有存储列，此项通常无须新增类型列。既有素材库可继续不显示类型编辑入口；新增请求字段不能改变其他客户端的默认行为。补充合法转换、被引用素材、冲突和无权限测试。

### C3. 镜头名称与卡片景别

建议给 `shot_scripts` 增加独立 `title`（最长 255 字符，旧记录默认空）和可空景别元信息，字段名建议为 `shot_size`。新增字段与枚举在本批固定到 Pydantic 和 DTO，不能用任意未验证字符串混充景别。

同步镜头创建、修改、读取、生成结果采用及 Service／DAO。当前生成结果已有 `title`，采用时写入名称；景别缺失时保留空值，不从脚本猜出“全景”作为真实数据。旧镜头空名称显示“未命名镜头”，原脚本、顺序、时长、关联素材和媒体完整保留。生成景别仅作元信息，不恢复用户已删除的景别设置控件。

标题修改走原单镜头保存队列与 `row_version`，图与视频页共用同一名称。判断媒体是否过期继续按来源版本和内容上下文处理，不以标题字符串代替已有校验。列表重新分页、排序、采用替换和刷新后名称必须稳定。

此项需要 ORM、真实 DDL、完整建库 SQL 及旧库增量迁移同步完成。只改 TypeScript 类型或只写迁移文件均不算实现。

### C4. Quill 格式与纯文本正文

采用 **Quill 2.0.3**，用局部 React 包装直接接入，不为此升级 React 或引入额外富文本框架。保留 BSD-3-Clause 许可；库通过正式依赖打包，静态 HTML 内嵌发行版仅作为设计证明。

推荐保留 `episode_scripts.content` 作为业务纯文本，并增加可空 `editor_document` JSON 保存受限 Quill Delta。正文与 Delta 在同一保存事务、同一 `content_version` 下更新；读取和恢复稿均同时带回两者。仅修改格式也纳入保存状态，不能显示“已保存”后刷新丢失格式。

服务端验证仅允许文本及确认的标题、加粗、斜体和引用属性；不接受脚本、图片或任意嵌入。明确统一纯文本转换：保留中文、用户空行与换行，区分 Quill 的结尾标记；校验纯文本与 Delta 一致，不以未经处理的 HTML 填入现有 `content`。

旧纯文本稿读取时生成展示用文档；旧客户端提交纯文本时重建或清除旧格式，避免格式与新正文错配。提取、生成、确认、导出和历史候选继续使用纯文本；生成候选只读，明确采用后才创建当前编辑文档，不能修改候选原始快照。场次识别只影响展示与定位，不自动改写正文。

扩展 [episode_writing.py](../../backend/src/short_drama/schemas/episode_writing.py)、正文保存 Service／DAO、ORM、前端 DTO、`WritingSession` 和恢复稿契约，并落实相应迁移。编辑器初始化、程序化载入用静默更新，用户编辑进入原串行队列；监听正确清理，避免 React Strict Mode 重复挂载、循环保存和输入法组合期间反复重建正文。

### C5. 个人生成草稿的自动保存

作品信息按项目现有规则共享；个人模型、补充提示词和下一次生成的参数草稿按本人保存。现有个人模型偏好仅保存配置选择，不能拿它冒充完整草稿，也不能把个人设置随素材或镜头作品共享。

保存方案建议采用独立私人草稿资源，实体名建议为 `user_creation_drafts`。范围由本人、项目、分集、稳定对象和生成用途组成；小说改编以分集为对象，素材图、分镜图、分镜视频分别保存。资源记录版本和源对象版本，内容包含模型配置 ID、输入文本、画幅、清晰度、张数／视频时长及个人参考媒体 ID。具体路由在契约批次定义为新增能力，不描述为已有接口。

服务器从可信 Actor 推导本人，验证项目／对象归属和模型、媒体访问权。模型秘密、签名 URL、Blob URL 不存入草稿；草稿 API 及读取结果仅本人可见。同步 Pydantic、DAO／Service、前端 API、ORM、建库 SQL、增量迁移和版本冲突测试。未完成服务端保存的输入只显示本机保留，不显示服务端已保存。

素材圆角框的画面要求通过现有生成 `input.prompt`（素材当前请求构造中的 `supplement`）传递；分镜图也可沿用补充提示词通道，保存来源下二者上限均为 4000 字符。个人输入不能自动回写共有素材 `description`／`prompt` 或镜头脚本。

当前分镜图校验请求中的画幅、清晰度及 `source.layout` 与已保存 `image_settings` 一致；视频有业务 `source` 时禁止同时提交 `input`，由服务端读取共享 `video_prompt`、`video_settings` 和已采用分镜图，且提交的时长、清晰度必须与保存设置一致。因此新增私人草稿后，不能原样把个人参数塞入当前请求，不能把私人输入偷偷保存到共享字段，也不能去掉 `source` 改走通用生成以绕过来源校验。

实施时扩展现有生成来源协议，允许显式引用已保存的私人草稿及其版本。服务端核对本人、对象、用途和草稿版本后读取并冻结内容，在共享作品上下文基础上构造实际生成快照：素材图和分镜图输入按补充语义处理；视频采用私人草稿提示词时仅替代本次视频提示词段，保留脚本和已采用参考图；图／视频的可见参数在本次任务内覆盖对应默认设置，隐藏 `layout` 沿用合法共享值。没有私人引用的旧请求继续使用现有保存来源语义。

生成前仍校验 `row_version`、`context_hash` 和当前采用参考图，任务快照同时记录私人草稿版本与实际使用参数。客户端不能直接信任草稿中缓存的来源版本，服务端也不能接受客户端拼出的最终提示词作为可信作品上下文。草稿保存未完成、版本冲突或采用图过期时阻止生成并保留输入；采用结果继续校验来源，不因接入私人草稿跳过既有保护。上述协议扩展已在 P0 实现：新增本人草稿资源，并通过 `source.draft_id`、`source.draft_version` 引用保存版本；无私人引用的旧请求继续沿用共享来源。当前契约与验证见[接口说明](../api/README.md)及实施验收记录。

个人参考图与既有共享来源参考图分别管理，提交时按永久媒体 ID 去重并共同校验模型上限，图片尤其验证 16／17 张边界。视频继续以当前采用分镜图为参考，不因通用视频接口支持多图就扩展本次布局。任何个人草稿字段都不能使当前采用图片或视频自动变化。
