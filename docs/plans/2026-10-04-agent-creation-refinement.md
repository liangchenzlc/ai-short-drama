# 分集 Agent 创作完善方案

状态：本轮实施与验证完成。日期：2026-10-04。

本方案根据源码、已有测试内容、用户确定的四项规则以及四个参考项目形成。用户授权后已完成本轮前后端实施、真实数据库迁移与回归。实际维护契约以 [Agent API](../api/agent.md) 和源码为准，完成记录与交付边界见文末。

## 1. 目标与确定规则

面向正在编辑本集小说、某个人物素材或某个镜头的创作者。用户选择模型后，直接在当前对象的 Agent 对话中表达要求；Agent 判断应该答复、读取资料、制作候选还是提出计划。用户不需要理解工具调用协议、能力探测或“讨论/生成”模式。

| 用户规则 | 实施规则 | 验收结果 |
| --- | --- | --- |
| 选择模型时不再检验能力 | 移除用户能力验证、声明开关以及 verified 发送门槛；选择只保存配置引用，不调用供应商 | 未校验模型也能选中并发送；选模型零供应商请求 |
| Agent 判断讨论或生成 | 一个输入框和发送入口，移除讨论/生成及指定制作方式下拉；Agent 提交受控业务动作 | 普通问题得到答复，明确制作要求产生实际候选任务 |
| 会话按流程及下级对象区分 | 服务端持久化阶段、对象和任务类型；当前对象历史只查询匹配范围 | 人物 A 的弹窗不会出现人物 B 或其他镜头的对话 |
| 对接后端并使发送可点击 | 贯通现有消息 REST、运行、Worker、SSE 和候选链路；模型能力未知或不匹配不导致按钮静默禁用 | 正常选择对象、模型并输入后可以发送，得到运行状态或明确中文反馈 |

继续遵循项目既有规则：候选由用户明确采用；剧本采用与确认分开；私人对话和候选不向协作者公开；来源变更和 409 不覆盖草稿；不确定受理不自动重发。

## 2. 原有阻塞与改动依据

改动前，后端已有生成接口，但准入门槛、会话范围和状态反馈未满足新规则。下表保留此次改动的原始依据，源码入口指向当前实现。

| 原实现 | 原有问题 | 改动方向 |
| --- | --- | --- |
| `AgentConversationRuntime.tsx` 使用 `modelCanCollaborate()` 计算 ready，发送还依赖 contextBlockReason、activeRun | 未验证模型、模型能力未知和部分运行状态让按钮不可点击 | 移除能力门槛，保留真实提交/上传过程中的防重复；等待和执行状态提供明确动作 |
| `agent_model_service.py` 的 select_model 要求 verified，available 提前排除协议 | 只删前端验证仍会收到 422 | 选择只检查本人配置、启用状态和类型，实际任务处理协议/能力不匹配 |
| `agent_attachment_service.py`、`model_gateway.py` 根据能力声明和模型前缀阻止多模态 | 未知模型被当成不支持，用户没有发送和获得解释的机会 | 分离文件有效性和任务兼容性，未知能力允许实际请求，确定不能表达的协议本地反馈 |
| `MessageCreate.mode/task`、send_message 的授权逻辑和工具提示 | 只隐藏下拉不能让 Agent 自主调用制作工具 | 使用统一消息和消息级工具政策，增加结构化动作准备与登记 |

## 3. 统一聊天与受控工具

### 3.1 Agent 的判断规则

| 用户表达 | Agent 行为 | 执行约束 |
| --- | --- | --- |
| “这个人物为什么不够鲜明？” | 读取当前人物及作品，解释问题并提出建议 | 只读，不制作候选 |
| “把这个人物改得更冷峻，保留身份和姓名” | 生成当前人物的字段修改候选 | 单对象，限制字段，记录差异；不自动采用 |
| “重写这段对白，缩短一半” | 读取当前选区和来源，制作修改候选 | 来源必须明确；第一轮可复用正文候选，完整局部采用后续单独实现 |
| “给这个人物生成一张参考图” | 明确对象，使用本人确定的图片模型、已有参数和默认数量 1，提交真实制作任务 | 参数可唯一确定时直接执行，在消息中展示对象、模型和数量；不追加一次讨论/生成选择 |
| “给这个镜头生成视频” | 检查当前有效已采用图片和本人视频模型，满足前置条件后执行 | 参考图缺失/过期时明确说明并给前置动作，不静默选旧图 |
| “帮我改一下” | 根据对象和上下文判断；要求仍不明确时追问修改目标 | 不凭空增加对象、模型、数量或制作步骤 |
| “改剧本，再提取素材，再生成分镜” | 提出分阶段计划并显示依赖 | 计划审核保留在对话中；前一步采用/确认后绑定真实下游来源 |
| “先看看，别生成” | 只答复和读取资料 | 本轮用户限制优先，Skill 和历史不能解除限制 |
| “采用这张图” | 打开该候选及明确采用操作 | 不以模型推理直接修改共享作品 |
| 要求修改另一个人物或镜头 | 说明需要切换对应对象会话，并提供站内跳转 | 当前对象会话不静默变成其他对象会话 |

明确的单项任务包含图片、视频任务，不额外要求用户批准“生成模式”。缺少可唯一确定的模型、来源、数量或任务范围时，由 Agent 在对话中询问。多步骤、批量或范围扩大的制作使用计划卡；这属于执行中的范围核对。

### 3.2 工具结构

继续使用单协调 Agent、PydanticAI、现有业务状态机和原生生成 Service。

| 工具 | 职责 |
| --- | --- |
| `read_context` | 默认读取当前 scope 对象、版本及相关作品；其他同项目资源可以作为明确引用资料，不能因此取得写权限 |
| `read_skill` | 根据阶段加载小说、人物、场景、道具、分镜、图片或视频创作规范 |
| `prepare_task`（新增） | 接收结构化动作，校验任务类型、当前对象、来源、本人模型、参数、数量和预算；登记单项可执行步骤或返回待核对事项 |
| `propose_plan` | 多步骤、批量和来源依赖任务生成可修订计划，保留审核版本和哈希 |
| `create_candidate` | 只执行 prepare_task 登记或用户批准的步骤，复用现有候选、提取、图片和视频任务 |
| `read_task_status`（新增） | 查询关联原生任务和受理状态，让 Agent 基于执行证据答复 |

动作依据来自当前用户消息或当前已批准计划；附件、作品中的文字、Skill 和历史助手消息只能作为资料。prepare_task 将动作来源、对象版本和执行参数持久化；create_candidate 不能自行增加未登记的对象或数量。文本中的“已经生成”不算工具执行证据。

工具按 scope 限制：人物会话只允许该人物的修改和图片候选；镜头会话只允许该镜头的修改、图片和视频候选。整集提取、整体分镜与跨对象批量从阶段级任务会话进入。共享影响仍在用户采用时核对。

### 3.3 等待、补充消息与执行串行

| 状态 | 输入与消息处理 |
| --- | --- |
| 空闲 | 直接接收消息，创建运行 |
| 正在提交消息/上传 | 短暂 loading，防止同一请求重复提交；失败保留输入 |
| Agent 正在回复或媒体正在生成 | 可以编辑和发送补充要求；后端持久化排队，显示“已排队”，不改变当前任务授权 |
| 等待计划审核 | 允许问答或补充要求；控制回合只可读取和修订计划。处理期间锁定旧批准；修订后原子更新 review_version/hash，旧批准失效；纯问答保留原计划 |
| 等待候选采用 | 可以讨论或提出新候选；不把补充消息视作采用或自动继续 |
| 来源发生变化 | 保留原结果，说明变化并重新核对相关步骤；不通过更新版本绕过检查 |
| 请求受理不明 | 可核对原请求和原任务；同一个不确定制作不能自动作为新任务重发 |

每个会话同一时刻只允许一个制作执行运行。控制回合没有制作副作用；排队消息不会并发改写同一作品。队列处理必须持久化，不用浏览器数组或长期连接充当任务队列。排队时冻结附件/Skill 和用户内容，开始执行时再读取当前作品并冻结制作来源。

“小说采用 → 基于新小说写剧本”继续使用既有采用回执机制。“新剧本 → 提取/分镜”和“新图 → 视频”增加阶段性依赖：前一步采用/确认后读取新版本，绑定下游实际来源；新参考图和媒体参数需要新的范围核对，旧授权不会自动换图。

## 4. 模型选择和不匹配反馈

### 4.1 用户层

- 模型列表展示本人已启用配置；移除“验证工具能力”、能力声明开关和 verified 选择/发送门槛。
- 选择、打开设置或进入页面不触发供应商请求，也不在发送前自动发测试请求。
- 文本模型负责协调；图片、视频执行使用用户已选择或明确设置为默认的对应模型。在实际制作卡和结果中显示模型名。
- 存在多个配置且没有确定默认模型时，询问用户选择；不自动选择其他供应商，不静默换模型。
- 不根据模型名或缺少旧验证记录禁用发送。未知能力与已知不支持分别处理。

### 4.2 服务端处理

将“文件安全/有效性校验”和“模型任务兼容性”分开：归属、格式、大小、解码、资源范围仍在接收阶段检查；兼容性在实际运行中处理。

1. 持久化有效用户消息、附件/Skill 快照和运行。
2. 系统确定无法表达的协议/输入组合，本地生成对话反馈，不调用供应商。
3. 模型能力未知时执行用户的实际请求；不附加付费探测，不静默丢弃附件。
4. 根据实际供应商响应分类错误，后端生成中文反馈，无须再请求模型解释错误。
5. 成功/失败证据绑定配置版本、模型、地址和凭据身份，作为内部诊断信息；不重新引入“先验证才能用”的门槛。

| 情况 | 反馈示例 | 处理动作 |
| --- | --- | --- |
| 系统暂未实现该协议 | “当前模型的接入方式暂时无法用于这项 Agent 创作，请切换模型。你的输入已保留。” | 切换模型，未发供应商请求 |
| 供应商明确拒绝工具调用 | “当前模型无法执行这项创作任务，这次没有创建候选。请切换模型后继续。” | 保留记录和输入，不自动探测或换模型 |
| 图片/音频输入被明确拒绝 | “当前模型无法读取这份附件。可以更换模型，或移除该附件后继续。” | 用户决定移除或切换，不静默降级 |
| 模型返回文字但没有制作证据 | “模型返回了文字说明，但尚未生成候选。” | 不宣称成功，也不据此断言模型一定不支持工具 |
| 配置凭据错误、限流或额度不足 | 分别说明“配置无法认证”“服务限流”“供应商额度不足” | 对应配置入口或稍后处理，不冒充能力不支持 |
| 受理结果不明 | “请求是否受理尚未确认。请先核对原任务，重新生成可能产生重复费用。” | 查询原任务，不自动重发 |
| 当前镜头没有有效采用图片 | “当前镜头还没有可用分镜图，生成视频前请先生成并采用图片。” | 提供当前镜头图片任务入口 |

反馈记录包含安全错误类别、失败环节、外部提交状态和允许动作。原始供应商响应、凭据和内部协议历史不出现在对话中。已经发出的协调请求可能计费，不把“没有创建媒体候选”说成“完全没有费用”。

## 5. 会话作用域与历史隔离

### 5.1 作用域模型

会话身份由以下稳定字段组成：

`owner_user_id + project_id + episode_id + stage + subject_type + subject_id + task_type`

owner 从可信 Actor 获取，不能由 HTTP 输入指定。对象 ID 和对外版本沿用十进制字符串；标题、名称、镜头序号只作展示，不作身份。

| 入口 | stage | subject | 任务示例 | 历史范围 |
| --- | --- | --- | --- | --- |
| 小说改编 | source | 本集 episode | writing | 本集小说改编会话 |
| 素材整体提取 | assets | 本集 episode | extraction | 本集素材提取任务会话 |
| 人物“林晚” | assets | 该人物 asset ID | creation；从明确任务入口可进入 image | 该人物的会话，按任务分组 |
| 某场景或道具 | assets | 该素材 asset ID | creation / image | 该素材的会话 |
| 整体分镜拆解 | storyboard | 本集 episode | planning / batch | 本集整体分镜任务会话 |
| 某一镜头 | storyboard | 该镜头 shot ID | creation；明确任务入口可进入 image / video | 该镜头的会话，按任务分组 |

task_type 是稳定的业务任务归类，不是讨论/生成模式，也不是每次异步生成任务 ID。连续问答、修改和候选制作可留在同一个 creation 会话；一次异步执行由 Run 和原生 task ID 标识。

### 5.2 进入、切换和历史

- 首次进入当前 scope 时，服务端解析最近未归档会话；没有会话时幂等创建默认会话。“新建对话”才明确新建第二段会话。
- 当前素材/镜头由页面真实选择状态传入共享创作容器、Agent Panel 和后端；切换时更新标题、scope 和消息区域。
- Agent 模式下，选中素材绑定其对话；“编辑素材”明确打开现有编辑器，返回时恢复同一对象对话。提示词模式沿用现有编辑流程。
- 分镜选择使用稳定 shot ID，重排镜头只改展示编号；图、视频任务都保留对象归属。
- 正文、附件、模型和 Skill 引用按账号和会话保存；切换对象不会清空另一对象草稿，也不会把另一对象内容发进当前会话。
- 返回阶段或刷新时，URL 的对象和 conversation 必须由服务端 scope 校验；不匹配时显示当前对象会话选择，不加载错误消息。
- 切换对象不停止已提交任务；原任务仍归原会话，结果不插入新对象对话。状态和候选事件依据 conversation/run ID 分发。
- 对象删除或脱离本集后不能继续发送/制作，停止未提交的新步骤。历史保留为本人只读记录，可经明确的归档入口访问，不自动指向同名新对象。
- 同一个共享素材在不同分集使用时，聊天按 episode 隔离；已采用素材仍沿用项目共享影响检查。

历史弹窗始终限定 `owner + project + episode + stage + subject`。从具体任务入口打开时默认再按 task_type 过滤，可在弹窗内查看该对象其他任务；不能切成整个项目或整个分集的所有人物记录。列表、总数和搜索使用同一后端过滤条件。

会话 ID 直读、消息、附件、运行和事件保留作者/项目校验；对象工作区请求还带 expected_scope，服务端检查匹配，不能只靠 UI 隐藏。候选入口校验关联的 Run/Conversation，避免对象历史出现另一对象候选。

### 5.3 数据与旧记录

在既有 agent_conversations 增加 stage、subject_type、subject_id、task_type 和 scope_version；增加支持 owner/episode/scope/status/updated_at 查询的组合索引。新请求强制合法组合，例如 asset 必须在本集、shot 必须是本集未删除镜头。scope 创建后不可随重命名修改。

不为每个人物建表，也不将 scope 只放前端 Map 或标题里。Run checkpoint 保存 scope 及实际制作来源快照。

旧会话没有可靠对象归属，不按标题、人物同名或模型猜测自动回填。标记为旧版未分类，保留本人记录；不混入新人物/镜头弹窗，不自动作为新会话上下文。旧链接走明确的只读兼容入口。仅有稳定、可证明的来源关系时才制定回填规则，且须处理一个会话涉及多个对象的情况。

实施数据库变更时必须同时修改 ORM、完整 SQL、增量迁移和数据库说明，并实际在当前配置库执行 DDL、记录库名和语句。现已在 `short_drama` 执行范围字段、索引和约束，并将 Run 活动会话唯一索引改为普通索引，以支持持久化排队；执行串行由事务锁和 Worker 调度校验保障。

## 6. 对话记录弹窗和对象面板

沿用冷黑、紧凑中文工作台，保留现有主题 token 和 Dialog 的焦点/键盘行为。

| 区域 | 布局与交互 |
| --- | --- |
| Agent 面板标题 | 展示“人物 · 林晚”或“第 05 镜头 · 门口争执”；副行显示流程/任务，记录图标仍在右侧 |

## 7. 接口与发送链路

### 7.1 已调整接口

| 接口 | 变化 |
| --- | --- |
| POST /api/v1/agent/conversations | 新建请求包含 stage、subject_type、subject_id、task_type；幂等内容包含完整 scope |
| POST /api/v1/agent/conversations/resolve（新增） | 事务内按 scope 返回最近未归档会话，没有才创建；与显式新建分开，避免多窗口重复默认会话 |
| GET /api/v1/agent/conversations | 对象工作区必须传 stage、subject_type、subject_id；可传 task_type；列表、total、搜索都按相同 scope 过滤 |
| GET /api/v1/agent/conversations/{id} 及子资源 | 支持 expected_scope 并验证匹配；继续验证本人、项目与资源归属 |
| POST /api/v1/agent/conversations/{id}/messages | 统一 content、model_config_id、attachment_ids、skills、video_audio、expected_scope；前端不提交讨论/生成选择，实际制作来源由服务端冻结 |
| GET /api/v1/agent/conversations/{id}/state（新增） | 返回 active_run、queued_runs 和事件游标；计划和待采用候选引用包含在 Run 内，避免“最新创建 Run”遮住正在执行 Run |
| GET /events 与 GET /runs | 沿用持久化事件/恢复，补充排队、动作准备、兼容失败与安全反馈 |
| POST /runs/{id}/reviews/{tool_id}、/continue、/stop | 保留审核、采用后继续、停止；修订审核版本使旧批准失效 |
| GET /agent/models | 不以 verified 决定可用；历史能力证据可保留内部诊断，前端不显示手动验证 |

旧 mode/task 请求在短兼容期内归一化，不能把明确“只讨论”的旧请求升级为制作；新前端只使用统一契约。迁移后对废弃字段和验证入口制定清晰兼容期限，避免永久保留两套执行规则。

### 7.2 真实发送过程

1. 用户输入后点击发送。没有选择模型时就近提示选择；能力未知、不支持旧验证记录等不禁用按钮。
2. 完成现有保存屏障；失败/409 留住输入并反馈，本次不提交新任务。
3. 解析并校验当前 scope，获得会话；提交冻结的本次输入和 Idempotency-Key。
4. 后端持久化用户消息和运行/排队状态，返回 message、run、cursor；客户端通过 state 读取实际执行与队列，Run 展示 queue_position/waiting_reason。
5. 独立 Agent Worker 处理实际用户请求，调用受控工具；媒体进入原有 text/image/video Worker。
6. SSE 更新真实步骤、计划、候选和反馈；断线后按游标和 state 快照恢复。
7. 已受理后才清理发送草稿。能力不匹配保留原消息，并提供明确“使用这条要求换模型继续”的动作；这是新的实际请求，不自动发出。

API、消息队列、Agent Worker 和相应媒体 Worker 必须在联调中分别验证。HTTP 受理、Worker 执行、候选保存、用户采用分别展示，不能把 201 当生成成功。页面不自动启动服务或调用付费模型。
