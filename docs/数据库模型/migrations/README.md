# 旧数据库升级入口

[完整建表脚本](../schema.mysql8.sql) 已包含当前全部 21 张表。新库只运行完整脚本；本目录保留旧库升级所需的增量 SQL、回填工具和操作说明。应用启动不自动执行迁移，也没有以目录存在与否判断升级状态的机制。

## 选择需要执行的迁移

按实际数据库结构和部署记录确认起点，从缺失的最早阶段向后升级；已完成的阶段不要盲目重跑。依赖表、字段定义或约束与预期不一致时，先解决差异，不能用“名称已存在”代替结构一致性核对。

| 顺序 | 迁移 | 适用旧结构及结果 |
| --- | --- | --- |
| 1 | [模型生成与资产库](2026-09-20-ai-generation/README.md) | 原业务表已有，缺任务/调用/生成媒体三表或配置能力缓存；`006` 单独处理仍有六种任务状态的旧版本 |
| 2 | [项目创建](2026-09-20-project-creation/README.md) | 删除旧 `projects.target_ms` 和对应 CHECK；删除值不可通过事务恢复 |
| 3 | [分集写作](2026-09-21-episode-writing/README.md) | 增加编辑剧本指针与 `content_version`，初始化未修改分集的编辑选择 |
| 4 | [生产工作流](2026-09-21-production-workflow/README.md) | 增加分镜集合/单镜头版本、归档与活动顺序、素材持久化及图片候选、采用上下文摘要；回填历史当前图片候选 |
| 5 | [分镜时长与原文依据](2026-09-22-storyboard-prompts/README.md) | 增加 `shot_scripts.duration_ms/source_excerpt` 及建议时长 CHECK |

第一批旧脚本显式含有 `USE ai_short_drama`，执行前必须检查目标库名并在审阅副本中按实际库名调整；其他迁移依赖连接已选定的数据库。不要在错误的默认数据库上执行，也不要把第一批脚本原样用于任意命名的新库。

## 公共执行边界

1. 使用 MySQL 8.0.21+、utf8mb4、UTC 和严格 SQL 模式。确认目标数据库、可恢复备份和现有表定义，记录受影响数据行数。
2. 暂停 API、调度器、Worker 和其他相关写入进程，按该迁移 README 执行预检、结构更新、回填及核验。生产工作流和分镜时长迁移依赖连接内临时基线表，预检到核验必须保留同一个 SQL 连接。
3. MySQL DDL 隐式提交，跨文件迁移不是一个可整体回滚的事务。失败时保留现场，从已执行状态核对重入条件，不删除业务表重新开始。
4. 核验字段、默认值、索引、CHECK 的表达式与启用状态、外键、行数和业务引用。结构以[当前数据库说明](../MySQL8数据表设计.md)及完整 SQL 为准；早期字段注释语言或列的物理排列可能不同，但不应有类型、默认值或约束的语义差异。
5. 部署兼容的新 API/Worker 后恢复写入。已产生新格式数据时优先向前修复；不要自动删除新增字段或恢复旧唯一索引。

文档不记录某个个人业务库“已经完成升级”的状态。发布人员应在部署记录中保存执行时间、脚本版本和验证结果。

## 测试

迁移测试保留在 `backend/tests/integration`，通过[开发说明](../../development.md)中的 `backend/scripts/run_integration.py` 运行。测试 fixture 创建随机隔离数据库，从当前总 SQL 建库，再在隔离库内模拟旧结构和历史数据，验证迁移、重入和数据保留。迁移 SQL 和 Python 回填是运维交付的一部分，不能因为它们不被运行时 import 就当作无引用代码删除。
