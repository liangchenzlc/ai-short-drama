## 1. 本轮结论与现状证据

1. 项目拥有的工具按业务子包、一工具一文件组织；外层保留 `registry.py`、`langchain.py`、`contracts.py`、`scope.py`。业务事务继续放在 Service，不能把工具拆文件变成拆散事务。

### 2.1 一份 ToolSpec 与薄适配

以下是类型边界关键片段。实际类型注解按锁定依赖及项目规范完善；`handler` 为业务 Callable 或已经存在的 BaseTool，不引入通用 ToolManager。

```python
from collections.abc import Callable
from dataclasses import dataclass
from typing import Any, Literal
from langchain_core.tools import BaseTool
from pydantic import BaseModel

ToolEffect = Literal[
    "read", "write", "submit", "context", "wait", "ask_user", "execute", "delegate"
]

@dataclass(frozen=True)
class ToolSpec:
    name: str
    description: str
    args_schema: type[BaseModel] | dict[str, Any]
    handler: Callable[..., Any] | BaseTool
    effect: ToolEffect = "read"
    expose_mcp: bool = False
    source: Literal["business", "runtime"] = "business"
    modes: frozenset[str] = frozenset()
    presentation: Callable[..., Any] | None = None
```

依赖方向固定为 `contracts ← 单工具模块 ← registry`；`langchain.py` 只从 contracts 导入类型。各单工具模块不导入 registry。`registry.py` 在构造目录时核对名称、来源与开放边界，并提供列表 / 查找；不再维护 `TOOL_SCHEMAS`、`OVERRIDES`、`HANDLERS` 的第二份定义。

业务 Callable 使用以下唯一适配。`invoke_business_tool` 是项目拟新增的业务调用边界；`ToolRuntime`、`BaseTool`、`StructuredTool.from_function` 是当前已核对的框架接口。本片段省略业务收据、审计、Session 和错误映射，不能作为完整实现直接运行。

```python
from langchain.tools import ToolRuntime
from langchain_core.tools import BaseTool, StructuredTool
from short_drama.agent.tools.contracts import ToolSpec

def create_langchain_tool(spec: ToolSpec) -> BaseTool:
    if isinstance(spec.handler, BaseTool):
        return spec.handler

    async def invoke(runtime: ToolRuntime, **arguments):
        return await invoke_business_tool(
            spec=spec,
            arguments=arguments,
            context=runtime.context,
            tool_call_id=runtime.tool_call_id,
        )

    return StructuredTool.from_function(
        coroutine=invoke,
        name=spec.name,
        description=spec.description,
        args_schema=spec.args_schema,
    )
```

项目 runtime 工具在自己的文件用 `@tool` 或 `StructuredTool` 定义真实工具；其 SPEC 的 name、description 都引用同一个工具对象，args_schema 取该对象的 `tool_call_schema`，过滤 ToolRuntime 等注入参数。框架原生工具也引用真实对象及公开 schema，保留公开名，不再包装一次。只有业务 Callable 进入上述适配和共用业务 Service；runtime handler 不经过另一个自写通用分派器。

`presentation` 是可信展示解析器，返回 `action / target / title`；target 使用统一的 `kind / id / display_name / version / path` 类型，资源片段的 offset、length 另存。调用开始依赖可信目录、scope 与冻结目标解析，完成后使用真实业务读回补全，不接受模型自行填标题。

`StructuredTool` 已继承 `BaseTool`。它提供 schema、调用与 ToolMessage 处理，统一为全部工具重写 BaseTool 子类只会增加同步入口及样板代码。仅当具体工具确实需要框架未覆盖的行为时，再单独论证继承，不将其定为项目约定。

参数在实际外部入口校验一次。内部使用已确定类型的值，不保留旧 schema 再校验一遍。可信 owner / run / scope / fence 来自 RuntimeContext 或 MCP 身份，不能成为模型可填写的参数。

### 2.2 effect、来源与对外开放

| effect | 含义 | 例子 |
| --- | --- | --- |
| `read` | 读取被授权的业务 / 运行资料 | 读取剧本、查询生成、读取 Skill 资源 |
| `write` | 持久修改作品、私有记忆或建议 | 保存标准增量、准备剧本建议、更新记忆 |
| `submit` | 幂等受理独立异步任务 | 提交媒体生成 |
| `context` | 改变当前范围的上下文 / 激活状态 | 加载或释放 Skill、记录工作笔记、导入文件 |
| `wait` | 显式等待系统任务，未完成时持久暂停 | 等待生成 |
| `ask_user` | 请求真实用户补充，持久等待回答 | 结构化问题卡 |
| `execute` | 在当前范围沙箱执行命令 | 框架 execute |
| `delegate` | 同步委派隔离子任务 | 框架 task |

effect 是目录及调用边界元数据，不根据它另写执行循环。只有工具实际遇到需持久等待的条件才调用 interrupt；不能在委派或命令一开始自动 interrupt。业务收据 Service 的 `mutating` 仍可由业务工具的 `effect in {"write", "submit"}` 推导，字段不用向模型暴露。

`expose_mcp` 由明确白名单控制，不能按 `read` 自动外放。MCP 只筛 `source=business and expose_mcp=True`；内部问答、等待、Skill、记忆、任务、沙箱与助手运行控制始终不外放。

### 2.4 输入、返回与交互合同

下表覆盖 28 项保留工具与 5 项新增工具，描述内部助手的目标合同；保留项按现名与 2.3 节对应，落地前缀同步修改目录和 Skill 依赖。输入只列主要业务参数，完整约束复用已核对的 [Harness registry override](../../backend/src/short_drama/agent/tools/registry.py)、[共用读取 schema](../../backend/src/short_drama/agent/tools/contracts.py)、[剧本 schema](../../backend/src/short_drama/schemas/assistant/operations/script.py)、[媒体请求](../../backend/src/short_drama/schemas/assistant/operations/media.py)、[Skill schema](../../backend/src/short_drama/agent/skill/contracts.py)及[观察 schema](../../backend/src/short_drama/agent/context/working_set.py)。新增项明确标注为设计，不把拟定字段描述成当前已经存在。

## 3. ask_user 的问题、回答与持久暂停

### 3.1 适用场景与 schema

`ask_user` 用于需要真实用户补充的信息、选择及决定。不为可合理推断的细节反复打断；它不是每次生成或写入前的通用确认闸门。问题与答案不修改权限、作品版本或部署政策。

问题请求采用受控 schema，不允许模型提交任意组件名、JavaScript 或完整动态 JSON Schema：

| 字段 | 约束 |
| --- | --- |
| `title` | 1–100 字，问题卡标题 |
| `question` | 1–4000 字，说明本次需要什么信息 |
| `allow_skip` | boolean，默认 true；false 时隐藏跳过，服务端拒绝 `outcome=skipped` |
| `fields` | 1–12 项，每项有 `key / label / type / required` 及受控可选属性 |
| `fields[].key` | 唯一稳定键，匹配 `^[A-Za-z][A-Za-z0-9_]{0,63}$`，不把展示文案作为字段身份 |
| `fields[].label` | 1–100 字且非空白；可选 placeholder 最长 200 字 |
| `fields[].type` | `text`、`textarea`、`single_select`、`multi_select`、`number`、`boolean` |
| `fields[].required` | boolean，默认 false；正常提交时必填项不能缺失、为空白或空列表；整组跳过只在 allow_skip=true 时有效 |
| `fields[].options` | 仅选择类使用且必填，1–20 项；每项 value 为 1–100 字稳定字符串、label 为 1–100 字非空白文案，value 唯一 |
| 字段回答 | text 最长 1000 字、textarea 最长 8000 字；single_select 为一个合法 value，multi_select 为不重复的合法 value 列表且最多 20 项；number 仅接受有限数值，拒绝 NaN、Infinity、boolean 和数字字符串；boolean 仅接受布尔值 |

每张卡固定提供有界的“补充说明”，不依赖模型记得添加“其他”。附件继续使用已有上传 / 选择入口，不在本次新增另一套文件回答通道。问题请求的字段名由服务端校验一次，前端使用固定映射渲染 Ant Design 控件。

回答 API 的顶层字段固定如下。此片段只说明契约；`question_version` 是该问题固定 schema / 正文的版本，不使用会随 interrupt 绑定变化的 Operation.row_version。

```python
class AskUserAnswer(InputModel):
    question_version: Identifier
    outcome: Literal["answered", "skipped"]
    values: dict[str, str | int | float | bool | list[str] | None]
    additional_text: Annotated[str, Field(max_length=8000)] = ""
```

服务端在回答入口按该 Operation 已保存的问题验证字段、类型、选项、长度和 required，拒绝未知字段键及非有限数值，不在内部再次定义另一份回答 schema。`additional_text` 最长 8000 字。`skipped` 明确表示整组跳过，values 为空且须 allow_skip=true；未提交、关闭卡片、离页、断线均不等于跳过。用户停止仍走 stop，不用 skipped 或空答案代替。问题参数验证失败返回工具错误，尚未创建有效问题或获得用户答复。

### 3.2 answer REST 与用户来源

```text
POST /api/v1/assistant/operations/{operation_id}/answer
Idempotency-Key: <本次回答的稳定请求身份>
body: { question_version, outcome, values, additional_text }
```

接口使用既有登录身份与 CSRF 规则，Service 在短事务内完成：

1. 验证当前账号拥有会话 / Operation，问题属于可信 Run / scope；越账号按现有不可见语义返回 404。
2. 先查已成功受理的请求身份及参数，命中即返回原回执，即使 Run 后来已经完成或停止；同键变参返回 409。同一个问题以新幂等键重发相同已存答案也返回原回执，不同答案返回 409，不能覆盖先前答案。
3. 只有尚未受理的新回答才检查问题仍待答、question_version 一致且 Run 未停止或终结，再按固定问题校验答案，保存真实回答者、答案、回答时间和用户消息身份；同事务写入事件及 ready 状态。
4. 返回受理结果、Operation / 用户消息身份与 cursor。可靠发布在图安全暂停后恢复同一个 Run，HTTP 请求不直接执行图。验收须覆盖“成功回答 → Run 完成 → 重试原答案”，仍返回原回执且不新增用户消息或恢复旧 Run。

答案保存为 `role=user / kind=tool_answer` 的真实用户消息，并通过 `answer_message_id` 关联该等待 Operation。模型结果使用服务端保存的结构化答案与消息来源引用，不接受客户端伪造 ToolMessage、namespace、interrupt ID 或任意 Command。来源查询与记忆引用规则须识别这种经过账号认证、属于本次提问的用户消息，不能把工具包装文本当用户原话。

普通消息受理与定向回答分开。定向答案只由目标工具消费一次，不创建 TaskInput，不再经过 sendTask 创建另一个 Run，也不能被普通新增输入 middleware 重复注入或推进普通输入水位。

### 3.3 复用 Operation 与 interrupt

不新增问题表。Operation.arguments 保存固定问题；Operation.wait_state 使用判别字段：

```text
kind: generation | user_input
共有：scope / tool call / namespace / checkpoint / interrupt / ready / consumed
generation：待结算的任务集合
user_input：question_version / answer / answer_message_id / answer_request_identity
```

以下是调用关系关键片段。`context.questions` 注入拟新增 QuestionService，其同步接口为 `register(..., request, fence)` 与 `read_answer(operation_id, fence)`；`@tool`、`ToolRuntime`、`interrupt` 是框架接口。完整实现还需要声明 SPEC、输入 schema、事务、事件及 fence，不可仅复制此片段上线。

```python
@tool("runtime__ask_user", args_schema=AskUserRequest)
def ask_user(runtime: ToolRuntime, **values) -> dict:
    """请求用户补充信息或选择；可以回答或明确跳过。"""
    context = runtime.context
    wait = context.questions.register(
        run_id=context.run_id,
        scope_id=context.scope_id,
        tool_call_id=runtime.tool_call_id,
        request=values,
        fence=context.fence,
    )
    interrupt({"kind": "user_input", "wait_operation_id": str(wait.operation_id)})
    return context.questions.read_answer(wait.operation_id, fence=context.fence)
```

登记按稳定 run / scope / tool call 幂等，恢复重跑保持相同 interrupt 顺序。问题登记与图 checkpoint 不是同一事务：答案先到时只记 ready；保存 checkpoint 后绑定 interrupt 的事务再次检查。checkpoint 已保存而绑定未提交时由 recovery 补绑，复用生成等待已有的竞态处理。

真实 interrupt ID 与完整 namespace 必须能从框架持久事实关联到 Operation。不能假设 ToolRuntime 自带 interrupt ID；工具内部 compiled 子图若不能被 `aget_state(subgraphs=True)` 递归发现，使用 saver 保存时已知的 namespace / interrupt / Operation 身份建立映射。

恢复使用服务端生成的 `Command(resume={interrupt_id: {"ready": True}})`。通知只是唤醒信号，答案仍从 MySQL 读取。多个问题分别关联，不能使用 Run 上单个“当前问题”覆盖。

### 3.4 前端状态、停止与子任务冒泡

Run / Task 增加 `waiting_input`，Operation 的等待状态、DTO、数据库约束、快照和事件一起修改。`waiting_input` 表示需要用户回答；`waiting_generation` / 媒体等待表示系统工作。子范围等待而其他分支仍工作时，根运行继续显示执行中，并列出待回答卡片。

问题卡默认显示标题、问题、字段、补充说明及“提交回答”；allow_skip=true 时提供“跳过”，false 时不显示。提交中禁重复操作，409 保留草稿并重新核对状态；已回答 / 已跳过 / 已停止显示持久结果。恢复查询必须返回未回答问题，不依赖只收到一次的 SSE。支持桌面键盘操作、内部滚动和最低 1280 CSS px，不新增移动端专用布局。

SSE 复用 AgentEvent 与 seq / cursor，增加问题请求、回答及取消的产品事件。事件只带可信 scope / 父调用 / Operation 关联，前端不解析框架私有节点名。客户端断线不取消问题。

用户停止根 Run 后，全部范围未回答问题变为 cancelled，后续新答案返回 409；已成功受理答案的幂等重试仍返回原回执，迟到事件不能恢复旧 Run。已受理媒体任务继续其独立生命周期，成果照常归档。停止后普通消息按既有规则新建 Run，不恢复旧问题。

这里 cancelled 是问题的展示状态：ToolCall 沿已有 cancelled，等待 Operation 使用 failed + agent_cancelled 结算，不新增未迁移的 Operation.cancelled。保留等待关联供查回与拒绝迟到答复，终态 Run 不再生成 resume map。

子 Agent 使用同一个 `runtime__ask_user`，scope 和父委派 ToolCall 由运行上下文注入。问题在主会话相应子轨迹展开，回答直接关联子图的 interrupt，不让父模型重新代问，也不创建可聊天的子 Conversation。

父 `task` 默认等待子任务交付。一个子问题不会取消其他独立分支；全部可执行分支完成或进入持久等待后，才释放根租约。回答只恢复对应子图，其他已完成分支不重跑。恢复必须根据持久 namespace / scope / 委派调用重绑定上下文；子图缺少 scope 时不能默默退回 root。

## 4. Skill 的三层渐进加载

保留已有导入、编辑、发布、不可变版本和手选能力。目标三层如下：

| 层 | 模型获得什么 | 不在该层做什么 |
| --- | --- | --- |
| L1 发现 | 常驻紧凑索引；按需搜索的名称、用途、适用 / 排除摘要、版本、真实工具依赖 | 不加载全部正文或资料 |
| L2 方法正文 | 模型选择某一冻结版本后，获得正文、完整 exclusions 与资源 manifest | 不复制整个资源包到模型或沙箱 |
| L3 具体文件 | 按需读某个资料片段 / 图片；或明确物化单个资源到当前沙箱 | 不自动执行脚本，不隐式导入全包 |

模型匹配任务后自动加载一个方法正文仍属渐进加载，不要求每次都先由用户手选。普通讨论不强制加载方法。用户明确选择、排除和修订优先，Skill 不扩大业务权限。

现状已有真实基础：[目录查询](../../backend/src/short_drama/service/skills/catalog/listing.py) 使用 summary 并延后正文 / 资源；`progressive.py` 按真实版本水合正文；`skill/runtime.py` 按需分段及读取图片；[transcript.py](../../backend/src/short_drama/agent/context/transcript.py) 保留活动正文的真实 tool call / result。应改造接入，不能引入另一套默认 SkillsMiddleware 接管同一产品状态。

### 4.1 四项真实缺口

| --- | --- | --- |
| 排除条件在模型投影丢失 | `skill_package.py` 解析 `short-drama-exclusions`；`markdown_parts` 移除 frontmatter；`progressive.skill_index` 与 load 返回未带 exclusions | L1 给紧凑排除摘要；L2 返回冻结版本完整 exclusions，供模型选择方法，不将自然语言排除条件冒充权限守卫 |
| search 盲裁描述 | `autonomous._search` 同样调用 `catalog_locked`；`progressive.py` 把所有 description 截为 180 字，所谓“分页目录仍有完整描述”的注释不成立 | 常驻索引继续短；搜索给与命中有关的有界发现信息、截断标记和继续发现位置，不为补发现信息提前 load 全文 |
| scripts 导入端到端被禁止 | `schemas/skills/catalog/skill.py` 的 ResourceKind 只有 reference/template/image，路径拒绝 scripts；`skill_package.py` 明确拒绝脚本；前端类型及导入文案同样不支持 | 一起扩展导入、编辑、发布、版本、manifest、资源读取与前端；只改沙箱执行工具无法补齐 |
| 激活状态只有 Task 范围 | `agent/skill/contracts.py` 从 task.effective_state 取 activations；release 只按 activation_id；资源资格未校验 execution scope | 激活 / release / resource read / materialize 都校验当前 scope；各子图状态独立，不共享一段 task JSON 读改写 |

这些缺口的源码位置分别见[包解析](../../backend/src/short_drama/service/skills/packages/skill_package.py)、[资源 schema](../../backend/src/short_drama/schemas/skills/catalog/skill.py)、[渐进加载](../../backend/src/short_drama/agent/skill/progressive.py)、[Skill 契约](../../backend/src/short_drama/agent/skill/contracts.py)、[前端资源类型](../../frontend/src/types/assistant/engine.ts)及[导入界面](../../frontend/src/features/skills/imports/SkillImportDialog.tsx)。

### 4.2 scope、冻结版本与正文保留

Run 开始时冻结当前可见 Skill 目录的身份、不可变版本引用及有界发现元数据，不读取正文或资源。`search_skills` 的分页查询沿该快照读取对应不可变版本，首次 load、release 后 reload 和故障恢复都使用原 pin；release 只撤销当前 scope 的上下文激活，不将版本切换为最新发布。目录、发布与非实时设置变更在下个 Run 生效；真实账号权限及资源访问资格撤销仍在读取 / 物化入口实时校验。

不可变的 version ID、包 checksum、资源 manifest 可以共享事实。`active`、`loaded_in_context`、资源读取和释放归属各自 scope；执行真源位于对应子图 / namespace 的 state，Task.effective_state 只能作产品投影。

子任务接收明确相关的紧凑索引、冻结版本和资料引用，按需自行 load；不复制父历史及全部活动正文。子 release 不改变父状态，父也不会自动获得子加载的正文。当前 scope 的 Skill 参数中不开放任意 `scope_id`，从 RuntimeContext 读取并由 Service 校验。

恢复时依靠持久 namespace → scope / 父委派调用关联重新绑定；ContextVar 仅是本次异步调用的便捷访问，不能成为持久身份来源。三个子图恢复、读取、物化与沙箱调用均须回到原范围，不能共用 root 激活列表。

单套摘要策略保留或按需恢复本 scope 活动正文对应的真实 AI tool call 与 ToolMessage，不能只留下 loaded 标记却丢失正文。release、手选替换和来源遗忘会使正文保留资格失效，摘要及 checkpoint 恢复不能复活被移除的内容。

沿用有界活动方法及资源预算。父子模型、selector、摘要的调用与输出计量归属同一 Run 账本；Skill 上下文配额不替代共享预算。恢复不因重建中间件而重新获得额度。

### 4.3 从脚本 manifest 到真实执行

新增 `ResourceKind=script` 与必要的 Python / Node 文本后缀，允许受限相对 `scripts/` 路径；其余路径、字节、包文件数和版本校验继续沿用现有边界。`requirements.txt`、`package.json` 等依赖清单仍是可按需物化的文本资料，不能因为位于 scripts 目录就全部算作可执行脚本。

读取、物化和执行分工明确：

```text
runtime__load_skill
  → 冻结正文 + 资源 manifest
  → runtime__read_skill_resource（需要理解某文件时，返回片段 / 图片引用）
  或 runtime__materialize_skill_resource（需要实际文件时，可直接按 manifest 物化）
  → 框架 execute（模型明确调用，才运行脚本或安装依赖）
  → runtime__export_artifacts（需要保存成果时，归档并返回引用）
```

物化不要求先把完整脚本读入模型上下文，也不自动执行。`runtime__materialize_skill_resource(activation_id, path)` 是真实可调用工具，不只在文档写一个模型无法触达的后台 helper。

处理流程为：读取当前 scope 的有效 activation → 核对冻结版本 / checksum / manifest 路径 → 调用 `agent/sandbox/resources.py` 导入当前 scope 的独立源目录 → 保存 Operation 与事件 → 返回实际相对路径、checksum、版本与 Operation ID。模型不能提交宿主路径、其他 scope、任意 MinIO locator 或当前发布版本来替换已冻结文件。

返回契约示意如下，仅说明结果形状，不表示代码已实现：

```json
{
  "activation_id": "123456789",
  "path": "scripts/prepare.py",
  "sandbox_path": ".skills/<版本checksum>/scripts/prepare.py",
  "checksum": "<实际文件摘要>",
  "content_version": "7",
  "operation_id": "123456790"
}
```

物化按 `scope + activation_id + 冻结 path + checksum` 幂等，重试和恢复查回原 Operation 与实际路径。冻结源位于 `/workspace/.skills/<版本checksum>/`，按只读用途保存；模型需要修改脚本、模板或输入时，显式复制到工作目录后编辑和执行，输出写入可写工作目录。该目录约定不构成脚本绝对不可写的保证；如果脚本改变导入源文件，下次 materialize 必须报告冲突或另存，不能静默覆盖。源文件只校验而不自动覆写。同名但不同 Skill / 版本使用各自版本身份与 checksum 路径；父子工作区隔离。

普通素材走 `runtime__import_resources`，Skill 文件使用 activation + manifest 专用入口，不能通过普通资源导入绕过 Skill 版本 / scope 校验。

Python 依赖安装到当前工作区 venv，Node 依赖安装到工作区项目目录；公网安装、下载和外部 API 请求沿主设计允许的沙箱网络能力执行，不另加正常联网确认。宿主 Worker 不执行 Skill 脚本，工具不获得后端密钥。

### 4.4 required_tools 与发现中间件

Skill 依赖查询统一 ToolSpec 目录，同时认可真实框架工具名。未知工具、当前模式不支持、尚未接入的外部来源分别说明；不安装外部 MCP 客户端补缺口。

基础必需工具放静态 `always_include`；活动 Skill 的 required_tools 在每次 ModelRequest 上，按当前 scope、权限及已冻结版本合并。不能修改共享 `LLMToolSelectorMiddleware.always_include` 实例字段，否则并行子任务会相互影响。合并顺序在 selector 之后，避免当前方法必需工具再次被筛掉。

框架 selector 的 `max_tools=16` 不包含 always_include，因此不是最终 schema 数量的硬上限。继续执行总上下文预算和工具可用性检查，不能依靠这个数字宣称所有工具 schema 必定不超过 16 项。

业务工具改为 workbench 前缀、运行工具改为 runtime 前缀时，同步内置包 required_tools、版本与摘要。已发布用户包不原地改写，创建新版本或明确缺依赖待升级；不保留永久旧名 alias。

## 5. 与设置、轨迹及主计划的衔接

本轮不把每个设置参数拆成独立版本。实时媒体政策保留既有 `media_generation_enabled / policy_version` API；关闭只限制后续受理，不撤销已外发任务。非实时 AssistantSettings 使用统一 `settings_version`，包含 `custom_instructions`、`model_call_limit`、`output_token_limit`、`subagent_max_concurrency`、`default_media_limits`，统一使用 `GET/PATCH /api/v1/assistant/settings`。Run 冻结实际设置，权限、停止和实时媒体政策在执行边界生效。

轨迹中的 action / target 从可信目录、scope、冻结版本及业务读回解析，不能让模型填写任意标题代替真实对象。聚合键为 `tool + target + version + scope`；问答、Skill 读取、物化、原生执行和子任务也保留真实调用身份，不能因折叠丢记录。

相对原计划 ToolSpec 的一致性变更为：类型移至 `tools/contracts.py`；`effect` 替换 `mutating`；handler 允许直接引用 BaseTool，args_schema 引用其真实公开 schema；presentation 统一可信展示解析。字段固定为 `name / description / args_schema / handler / effect / expose_mcp / source / modes / presentation`，不新增第二个运行工具注册表或前端名称表。

新增 / 重命名工具、Skill schema、waiting_input、answer API 和定向来源处理应进入主计划对应任务；本文件不重复庞大验收矩阵。设置与轨迹边界见[主设计第 11 节](2026-10-29-创作助手运行时与工具扩展重构设计.md#11-前端执行轨迹与设置)，执行命令与交付证据要求见[主计划第 5 节](../plans/2026-10/2026-10-29-创作助手运行时与工具扩展重构实施.md#五交付验证与范围声明)。
